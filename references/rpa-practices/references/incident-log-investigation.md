# 影刀专项日志查证与现场交付

只在用户明确要求调查某次 RPA 运行的日志或故障时使用。不适用于晨检、日报或日常巡检，不改变它们的检查、交付或录屏规则。

## 先核对运行，再解释故障

1. 用实际运行机的任务历史和日志确认：机器（主机名或约定标识）、RPA 名称、运行日期或任务 ID、实际加载的应用版本或源码，以及涉及的 Sheet、业务环节或店铺。不能用开发机当前源码代替运行时版本；核验不到时明确说明。
2. 报告开头写「机器｜RPA｜店铺（如适用）｜日期」，下一行写结果：还有什么未完成、是否需要处理或补跑。
3. 按异常 Sheet 或业务逐项列。每项单独用「**HH:mm:ss**｜具体失败步骤」开头，标运行机日志里首次确认报错的北京时间。简述上一步做到哪、在什么页面对哪个元素或目标做什么时失败、后续哪一步未执行。不把查找、点击、等待、下载和写入混为一谈。不拿视频进度当实际时间；无日志时钟就说明。区分事实、推测和待查事项。
4. 同一对象同一步的重试合并；跨轮复现可写轮次，不默认罗列每次报错时间。已确认恢复只写「后续已补写并保存」或「后续已自愈」，不列恢复、补写、保存的时间。后续一轮成功不等于原对象已经恢复，须有同一对象的证据。完整录屏路径集中放末尾；任务 ID、毫秒、报错原文等按需另附，不默认铺在正文里。

### 在运行机只读查任务

已有 Task ID 时从状态或日志查询开始。否则用 `console task history --page 1 --page-size 20` 查第一页，按应用 ID 和创建时间匹配，再按需翻页。用 `console task status --task-id <任务 ID>` 核对对应状态。用 `console task logs --task-id <任务 ID> --limit 50` 获取日志。若 `hasMore` 为真，下一次查询加 `--cursor <nextCursor>`。命令使用运行机上的官方 CLI，参数以当地子命令帮助为准。

Windows 影刀 6.4.14 的一次只读核验中，`history` 和 `status` 没有返回 `versionId`。当前线上版本只能证明当前发布状态。历史运行版本可用同一任务可关联的运行机主日志、发布记录或当时部署产物另行核对。关联不到时标为「实际加载版本未确认」。

## 原始现场录屏

- 在 Markdown 聊天里，录屏路径放在报告末尾：每个完整 Windows 共享路径单独占一个代码块，轮次和说明写在代码块外。原样保留开头两个反斜杠（示意：`\\服务器\共享\录屏.mp4`），避免聊天排版吞掉一个。

- 核对录屏与日志是同一运行机、同一任务或已核准的时间段，并包含所查动作。只交付已录制完成、关闭并核实可读的相关原始 MP4；不使用仍写入的文件、近似或其他运行的录屏冒充证据。
- 仅在适用本专项且复制获授权时交付原始 MP4。用户没有为本次另指定目录时，从 Windows 开发机本地 `%USERPROFILE%\Desktop\.rpa-incident-recording-dir` 读取唯一的现行中转路径；其他环境在可访问的 Windows 开发机上读取该配置。配置不得放进项目或公开仓库，不要回退到历史路径。
- 在授权范围内复制符合条件的录屏，核对目标可读和文件大小一致，再报告完整文件路径。没有同一运行的已完结影片、没有安全的共享范围、配置缺失、共享不可达或未获授权时，明确说明没有交付录屏，不默认复制一批文件或发送原始日志。
