# 多数据源报表安全边界

本文适用于“多个数据源或多个更新任务写入同一目标工作簿”的项目。单个 API、单个数据源或各自保存到独立文件的任务，不要机械套用。

## 先分别确定业务失败策略与 Excel 提交策略

不要把“某个数据源失败是否继续”和“工作簿什么时候保存”混为一谈。设计时分别确认两个维度：

- **业务失败策略**：所有必需来源缺一不可，失败就中止；或者来源本身独立，下载 / 准备失败可记失败后继续其它无依赖任务。存在依赖时只允许使用已满足时效要求的来源。
- **Excel 提交策略**：在一个工作簿对象中更新完后**统一保存一次**；或者业务明确需要已成功任务立即持久化，**每个任务分别提交**。一次打开不自动等于所有下载都必须成功，允许部分下载失败也不自动要求逐任务保存。

### 单工作簿、整轮统一提交

适用于用户需要一次打开 Excel、连续更新多个 Sheet、最终只保存一次的场景：

1. 主流程准备目标文件的临时副本，明确打开一次 `workbook`，并将其传给每个 `update_xxxx` 业务模块。
2. 下载 / 数据准备在修改工作簿前完成必要校验。业务允许独立失败时，只记录本来源失败并继续处理其它来源，最后可提交已成功的更新。
3. **任何工作簿写入中途失败都可能留下半成品**：终止本轮写入，关闭并丢弃临时副本，不提交此前未保存的修改，也不把这些修改报告为成功。
4. 所有可继续的任务结束后，只保存一次并关闭工作簿，最后原子替换正式文件。保存、关闭或替换失败时按未提交处理；最终通知应反映真正落盘的结果。
5. 若用户可同时编辑正式文件，提交前检查占用及外部修改，防止覆盖用户的新修改；不要仅依赖启动时的一次锁检查。

如果多个来源共同组成一个不可拆分的业务结果，则应额外要求**全部必需来源成功才统一提交**，不能因为采用单工作簿就忽略这个业务条件。

### 各任务分别提交

只有明确要求独立任务可以先保存、后续任务失败也不影响前面已落盘结果时，才采用逐任务提交：

1. 每个任务的业务数据及成功状态在同一次独立事务中提交；失败不得保留该任务的半成品业务数据。
2. 单个任务失败不阻塞其它无依赖任务；任务成功时间、重试规则及跳过条件按本项目业务约定，不预设统一运行开关。
3. 存在依赖关系时只阻塞依赖链，例如 B 依赖 A，A 失败不应阻塞无关的 C、D。

两种提交模式都应保留必要的上一次成功时间与失败原因；**最近成功时间只能代表已成功落盘的数据**。最终结果通知优先在完整流程结束后统一发送，各模块不单独发送最终汇总。

单工作簿过程式写法可参阅 [完整最小 Demo](examples/multi-sheet-workbook/README.md)；该 Demo 不是实时 ERP 导出实现，也不证明特定版本 WPS 的公式自动重算行为。

## 主流程

```text
读取已有业务配置 / 建立必要会话
→ 按已确认的失败策略准备并校验数据
→ 明确打开工作簿和交给业务模块的对象
→ 按已确认的提交策略保存（整轮一次或逐任务提交）
→ 关闭工作簿和页面
→ 发送一次最终通知
```

主流程应从上到下直接阅读。不为了形式统一引入巨型 `context`。

## 数据源模块

独立数据源只在代码量较多、业务边界清楚且拆出后更容易阅读时建立模块。同类模块可统一采用 `update_xxxx.py` 命名；入口只接收实际需要的页面、会话、配置或目标工作簿，不传入包含所有状态的大字典。若一类业务更新需要复用多个国家 / 站点的同一计算规则，可由一个业务模块集中实现。

成功协议只选一种：

- 成功正常返回，失败抛出异常；或
- 项目已有显式布尔协议时，主流程严格检查 `is True`。

不混用“部分函数抛异常、部分函数返回 `None`、部分函数返回布尔值”的成功判断。

## Excel 写入安全

- 覆盖目标区域前，使用本轮已读取的数据确认当前业务必需的表头、列映射、数据范围和目标区域，并按已确认的业务约定判断空结果是否允许覆盖；无法确认时停止该数据源，不清空旧数据。不增加重复读取或全量预检。
- 覆盖型数据：只清空约定的数据区域，不整表 `clear()`，避免删除公式、格式和其他业务区域。
- 追加型数据：先确认最后日期或最后数据行，只追加缺失数据。
- 商品 ID、订单号、链接 ID 等长数字写入前按文本处理，避免精度丢失。
- 下载步骤必须检查返回路径非空且文件存在，不把“已点击下载”当作“文件已可用”。
- 如果 RPA 有一张完整的更新状态表，应按其表头及数据行整体读取、检查并转换状态字段，避免仅为当前一个判断拆散完整业务表；但不因此要求普通业务查询全量读取不需要的数据。
- 一个工作簿会话内先更新原始区、后读取公式计算区的项目，应在真实 Office / WPS 中验证公式是否刷新；不得以 Python 模拟成功替代真实公式结果验收。

## 异步导出任务绑定

网页后台常见“点击导出 → 后台生成任务 → 下载列表出现文件”的异步流程。触发导出后，不能只按“文件类型 + 今天 / 当前小时”等粗粒度条件匹配第一条记录，否则同一时间窗口内已有旧任务时，可能下载旧数据并误报成功。

推荐顺序：

1. 触发导出前，记录当前导出任务集合、任务数量或其它可稳定比较的现场信息。
2. 记录本轮触发时间，再执行导出动作。
3. 优先使用任务 ID、精确创建时间、唯一任务名等稳定标识定位本轮任务。
4. 页面没有唯一标识时，至少用“触发前快照 + 触发时间 + 新增记录”联合判断本轮新增任务。
5. 等待**这个新增任务**进入可下载状态后，再点击它的下载按钮。
6. 下载完成后继续校验本地文件确实属于本轮任务；本地文件创建时间只能作为辅助证据，不能替代网页端任务绑定。

### 多地区、多任务分类

一个后台可能按地区 / 店铺隔离导出任务，并在同一个“任务中心”弹窗内通过不同页签展示商品、库存等任务。对此应把**地区 / 店铺 + 任务分类 + 本轮新任务**作为完整定位上下文：

1. 切换地区前先打开地区选择器；选择后等待页面地区、实际 URL / 店铺标识和目标业务页面都更新，不能只因下拉标签变了就继续。
2. 每次进入任务中心后，显式切换到当前导出所属的任务分类；不要假设它默认展示正确的分类，或把不同分类下名字相近的导出当作同一数据源。
3. **每个地区分别**建立导出前任务快照和本轮提交时间，确认新增任务后等待其成功并下载；切换下一地区时重新建立快照，不跨地区沿用上一轮任务集合。
4. 不同地区可能导出同名文件；下载后分别保存并标记地区，确认文件身份和数据布局后再拼接，避免后下载的文件覆盖先下载的文件。
5. 同一最终 Sheet 依赖多个地区文件时，全部地区文件都成功且结构一致后，才提交这个 Sheet；失败只阻塞该 Sheet，不扩大到其它独立 Sheet。

如果无法可靠区分本轮任务与历史任务，应停止该数据源并保留旧数据，不要为了继续流程随便取第一条“看起来最新”的导出记录。

压缩包解压和解压后多文件目标识别见 [xzip.md](../xbot-api-docs/docs/xzip.md)。

Excel / WPS 具体 API 见 [excel.md](../xbot-api-docs/docs/excel.md)。

## 重试与日志

项目存在显式重试时，每次尝试开始记录尝试次数和必要业务上下文；失败时在异常处理中记录当前业务步骤及 `traceback.format_exc()` 完整堆栈。成功后停止重试；达到项目规定的最大次数仍失败时，在最后一次失败对应的 `except` 中发送一次失败通知后直接 `raise`，需要增加业务上下文时使用 `raise ... from exc`，不要把异常保存到变量后脱离原 `except` 再重新抛出，也不要静默结束。

页面打开、下载等待、验证码处理、解压、工作簿写入和最终保存等关键阶段应有可定位日志；日志服务于定位当前业务步骤，不为了“完整”给每个简单赋值和基础调用都加日志。

页面、XPath、Sheet 名、写入区域、日期口径和市场指令参数仍以当前项目为准，不从本文猜测。
