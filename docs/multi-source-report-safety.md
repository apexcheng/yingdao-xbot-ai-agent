# 多数据源报表安全边界

本文适用于“多个数据源或多个更新任务写入同一目标工作簿”的项目。单个 API、单个数据源或各自保存到独立文件的任务，不要机械套用。

## 先分别确定业务失败策略与 Excel 保存策略

不要把“某个数据源失败是否继续”和“工作簿什么时候保存”混为一谈。设计时分别确认两个维度：

- **业务失败策略**：所有必需来源缺一不可，失败就中止；或者来源本身独立，下载 / 准备失败可记失败后继续其它无依赖任务。存在依赖时只允许使用已满足时效要求的来源。
- **Excel 保存策略**：在一个工作簿对象中更新完后**统一保存一次**；或者业务明确需要已成功任务立即持久化，**每个任务分别保存**。一次打开不自动等于所有下载都必须成功，允许部分下载失败也不自动要求逐任务保存。

### 单工作簿、整轮统一保存（默认写法）

适用于用户需要一次打开 Excel、连续更新多个 Sheet、最终只保存一次的场景：

1. 主流程在打开前按项目约定检查正式文件占用，直接 `xbot.excel.open(file_name=str(target), kind="wps", ...)` 打开正式工作簿一次，并将同一个 `workbook` 传给每个 `update_xxxx` 业务模块。
2. 下载 / 数据准备在修改工作簿前完成必要校验。业务允许独立失败时，只记录该来源失败并继续处理其它无依赖来源。
3. 工作簿写入中途失败时，停止后续写入，不主动调用 `save()`；异常关闭时按已确认的 WPS 接口处理未保存改动（例如 `set_saved(True)` 后关闭）。不要把未保存结果报告为成功。
4. 所有可继续的任务结束后，无论是否全部跳过，调用一次 `workbook.save()` 并关闭工作簿。

**保存边界：** WPS 自动保存、保存失败或异常退出时，需核实正式文件的实际状态。

如果多个来源共同组成一个不可拆分的业务结果，则应要求**全部必需来源成功后才保存本轮结果**。

### 各任务分别保存

只有明确要求独立任务可以先保存、后续任务失败也不影响前面已落盘结果时，才采用逐任务保存：

1. 每个任务的业务数据及成功状态应在该任务确实完成后一起保存；失败时不主动保存该任务未完成的修改。
2. 单个任务失败不阻塞其它无依赖任务；任务成功时间、重试规则及跳过条件按本项目业务约定，不预设统一运行开关。
3. 存在依赖关系时只阻塞依赖链，例如 B 依赖 A，A 失败不应阻塞无关的 C、D。

两种提交模式都应保留必要的上一次成功时间与失败原因；**最近成功时间只能代表已成功落盘的数据**。最终结果通知优先在完整流程结束后统一发送，各模块不单独发送最终汇总。

单工作簿过程式写法可参阅 [完整最小 Demo](examples/multi-sheet-workbook/README.md)；该 Demo 不是实时 ERP 导出实现，也不证明特定版本 WPS 的公式自动重算行为。

## 主流程

```text
读取已有业务配置 / 建立必要会话
→ 按已确认的失败策略准备并校验数据
→ 明确打开工作簿和交给业务模块的对象
→ 按已确认的保存策略保存（整轮一次或逐任务保存）
→ 关闭工作簿和页面
→ 发送一次最终通知
```

主流程应从上到下直接阅读。不为了形式统一引入巨型 `context`。

## 数据源模块

独立数据源具有清楚的业务边界或实际复用价值，且拆出后更容易阅读时，可以建立模块，不以代码行数为门槛。同类模块可统一采用 `update_xxxx.py` 命名；入口只接收实际需要的页面、会话、配置或目标工作簿，不传入包含所有状态的大字典。若一类业务更新需要复用多个国家 / 站点的同一计算规则，可由一个业务模块集中实现。

成功协议只选一种：

- 成功正常返回，失败抛出异常；或
- 项目已有显式布尔协议时，主流程严格检查 `is True`。

不混用“部分函数抛异常、部分函数返回 `None`、部分函数返回布尔值”的成功判断。

## Excel 写入安全

- 覆盖目标区域前，使用本轮已读取的数据确认当前业务必需的表头、列映射、数据范围和目标区域，并按已确认的业务约定判断空结果是否允许覆盖；无法确认时停止该数据源，不清空旧数据。不增加重复读取或全量预检。
- 覆盖型数据：只清空约定的数据区域，不整表 `clear()`，避免删除公式、格式和其他业务区域。
- 追加型数据：先确认最后日期或最后数据行，只追加缺失数据。
- 商品 ID、订单号、链接 ID 等长数字写入前按文本处理，避免精度丢失。
- 下载步骤必须检查返回路径非空且文件存在。网页后台异步导出时按 [本轮导出任务绑定](async-export-task-binding.md) 定位对应文件。
- 如果 RPA 有一张完整的更新状态表，应按其表头及数据行整体读取、检查并转换状态字段，避免仅为当前一个判断拆散完整业务表；但不因此要求普通业务查询全量读取不需要的数据。
- 一个工作簿会话内先更新原始区、后读取公式计算区的项目，应在真实 Office / WPS 中验证公式是否刷新；不得以 Python 模拟成功替代真实公式结果验收。

Excel / WPS 具体 API 见 [excel.md](../xbot-api-docs/docs/excel.md)。

## 重试与日志

项目存在显式重试时，记录尝试次数和必要业务上下文；失败现场只在需要保留异常现场的层记录 `traceback.format_exc()`，上层统一记录完整堆栈时中间层不重复输出。成功后停止重试；达到最大次数仍失败时，按项目既定失败策略处理：允许隔离失败的，记录失败状态并继续其它无依赖任务；需要终止或上抛的，在对应 `except` 中直接 `raise`，需要补充上下文时使用 `raise ... from exc`。已有统一通知机制时不重复发送失败通知，也不要静默结束或脱离原 `except` 重抛异常。

页面打开、下载等待、验证码处理、解压、工作簿写入和最终保存等关键阶段应有可定位日志；日志服务于定位当前业务步骤，不为了“完整”给每个简单赋值和基础调用都加日志。

页面、XPath、Sheet 名、写入区域、日期口径和市场指令参数仍以当前项目为准，不从本文猜测。
