# 影刀编码版编程风格详解

`project-template/AGENTS.md` 中的“代码结构与编程风格”是真实影刀项目必须直接遵守的硬约束。本文只承载完整判断、示例和低频边界，不能用来降低或替代项目规则；普通小改无需加载全文。

## 1. 过程式主流程

- 业务顺序应直接反映真实执行顺序，例如：读取 → 判断 → 操作 → 写回 → 保存 → 通知。
- 如果业务要求“采当前页 → 写当前页 → 展示 → 下一页”，代码也保持这个顺序；未经用户要求，不改成先采集全部页面再统一写入。
- 不为了形式统一引入巨型 `context`，避免主流程在多个文件和函数之间反复跳转。

## 2. 文件职责

- `run.py` 是 Code 流入口，保留影刀调用约定 `main(args)`，并让主业务顺序直接可见。只有明确对接现有流程参数时才读取 `args`；其他模块按正常 Python 语法调用。
- `config.py` 保存当前项目需要的配置变量、配置路径或稳定静态设置，不承载主业务流程；默认不使用影刀“运行应用时需要传入的参数”作为配置来源。
- 已有 `tool.py`、`utils.py`、`win_utils.py` 时，只放稳定且真正复用的公共能力。不要为了统一命名新增另一套工具文件，也不要把单次业务步骤搬进去。

### 同类业务更新的模块边界

当多个店铺、站点或国家复用同一套计算与更新规则时，可由**一个业务模块**负责这些对象的顺序、业务特有依赖、逐对象跳过和结果处理；主入口仅调用一次完整的业务更新阶段。不要把同一业务的前半段计算放在模块内、后半段专属更新编排长期留在 `run.py`。

工作簿的打开、最终保存、关闭及统一通知应在主流程直观看到；业务模块按需接收本轮共享的工作簿对象。WPS 日常更新直接打开正式文件，业务结束后 `workbook.save()` 并关闭；不要把 Excel 生命周期藏进多层回调，也不要反向导入 `run.py` 制造循环依赖。逐任务保存或整轮统一保存按 [多数据源报表安全边界](multi-source-report-safety.md) 中的业务条件判断。

### 关键对象生命周期与完整业务对象

- Excel / WPS、浏览器会话等需要显式创建和收尾的关键对象，其拥有者应明确。多模块共享同一个 Excel 时，`run.py` 直接打开工作簿、把 `workbook` 传给各业务模块，最后根据业务提交策略保存、关闭；不要让每个更新模块自行反复打开同一工作簿。
- 同一类 Sheet 的更新模块可统一采用 `update_xxxx.py` 命名；一个模块承接多个同规则国家、站点或店铺的更新，而不是机械按每张 Sheet 再拆文件。名称是项目内一致性约定，不是适用于所有 RPA 的强制命名空间。
- 读取“完整业务表格”时，应按其数据契约一次获取表头与所需的完整记录，校验结构，再将所有有业务意义的字段转换为统一结构。例如 RPA 更新状态表包含对象名称、成功时间、尝试时间、结果和说明，不应只因为当前跳过判断使用成功时间，就把其余字段永久丢弃或割裂成多次读取。这并不要求一般查询读取无用列；是否完整读取由业务对象边界决定。
- Excel 公式依赖源区刚写入的数据时，必须用实际 Office / WPS 行为确认同一次打开且未中途保存的公式读取结果是否已刷新；未验证前不能假设及时重算，也不要猜测强制计算 API。

可借鉴的最小多文件示例：[多 Sheet 工作簿过程式更新 Demo](examples/multi-sheet-workbook/README.md)。它是教学示例，不是经过影刀实机验收的业务项目。

`main(args)` 可保留作为影刀 Code flow 的固定入口签名。若项目没有明确约定接收外部 Flow 运行参数，不必添加 `args = args or {}` 或 `args.get(...)` 兼容链；确实需要的稳定业务设置再从 `config.py` 读取。

RPA 默认只实现当前确定需要的运行方式：固定业务顺序就直接执行，不为方便未来调试预设 `force`、`only_sheets`、单项补跑等额外开关、筛选分支、参数转发或专门状态。先判断是否存在真实业务使用场景，再决定是否增加配置；不能只因选项易实现或“以后可能用到”就保留。已明确要求的今日成功跳过、实际数据依赖、失败隔离、任务绑定和通知不属于过度设计。

### 数据获取与业务判断分离

- 数据库查询、接口查询、CSV / Excel / 文件读取等数据获取代码，默认负责“把实际结果拿回来并按其技术契约解析好”，不要顺便替当前调用方决定这个结果在业务上是否可接受。
- 例如查询结果是 `0 / 1 / N` 条、接口返回空列表、读取结果为空，这些事实本身不等于异常；当前业务要求“必须唯一”“不能为空”“没有则跳过”时，由实际业务调用方就地判断并决定 `raise`、跳过或继续。
- 数据获取层仍然处理自己的技术问题：SQL 执行或事务失败、HTTP / API 请求失败、响应结构不符合已确认接口契约、文件无法读取或格式损坏等，可以在该层直接抛出或自然传播异常。
- 不要把某个具体业务的规则写进通用数据获取函数。同一个查询或读取能力，在不同业务里可能分别要求唯一命中、允许多条、允许为空；数据获取函数应返回实际结果，由不同业务分别解释。

```python
# 业务调用方：根据当前业务规则解释结果
records = data_source.query(query_value)
if len(records) != 1:
    raise RuntimeError(f"当前业务要求唯一命中，实际匹配到 {len(records)} 条")
record = records[0]
```

## 3. 变量与内联

- 单次使用的字面量、简单属性、简单表达式或立即调用结果直接写在使用位置。
- 只有值会复用、后续还要读取或判断、表达式较复杂、命名能解释业务含义，或必须保留对象状态时才提取变量。
- 只为紧接着调用一次方法、读取一次属性或继续一次简单转换而创建的中间变量没有额外语义，直接链式表达；不要为了“步骤清楚”把一次性连续操作拆成多个变量。
- 简单赋值不要先初始化占位值，再用紧接着的短 `if` 覆盖同一变量。若只是清晰的二选一结果，直接用一次条件赋值；分支包含多个业务动作、异常处理、副作用，或条件表达式明显降低可读性时再展开 `if`。
- 能在使用位置直接读取或计算的值就地处理，不为了“统一管理”放入全局变量、字典或长期中间状态。
- 函数和方法调用在保持可读时写在一行；参数很多或结构复杂时正常换行，不把“一行”当成损害可读性的硬格式。

```text
非执行调用说明（不可直接运行）：
# 单次使用，直接内联
page.find_by_xpath("//button[contains(., '下一页')]", timeout=3).click()

# 一次性元素对象继续读取文本时直接链式调用
serial_text = row.find_by_xpath(
    ".//*[contains(@class, 'sku-serial-number')]",
    timeout=3,
).get_text().strip()

# 简单二选一结果直接一次赋值
erp_match = re.search(r"商家编码\s*[:：]\s*(\S+)", serial_text)
erp_code = erp_match.group(1).strip() if erp_match else ""
```

## 4. 函数与类

- **一个 Page、一个业务主函数。** 页面切换、查找、筛选、点击、任务中心、导出、下载、等待及结果判断在同一函数内按顺序展开；多地区或多店铺的相同页面操作在该函数内循环。即使其中一个步骤在当前 Page 重复，也不因此独立封装。
- **辅助能力按真实边界封装。** 复杂动态日期筛选、登录并取得可用 Page、跨业务复用的通用工具、独立数据处理可以提取函数；不因为函数较长、某步骤有输入输出或想缩短主函数而拆分页面动作。
- **参数与状态只传必要内容。** 函数接收实际需要的值；稳定项目配置由使用它的业务模块从 `config.py` 读取，运行时输入和被覆盖的配置按业务边界传递。通用底层函数仍通过参数接收所需信息。
- **类按对象职责选择。** 围绕同一对象共享必要状态、生命周期并提供清晰接口时可以使用；普通业务不为分组函数或预留扩展而增加抽象层。日志等基础设施按实际职责判断。

### 每一层只暴露需要理解的概念

上一层只保留当前业务需要的输入、结果和控制流程；字段解析、索引等实现细节留在当前层，降低调用方需要同时理解的信息量。

例如分页采集流程，以下是**同一 Page 主函数内部的执行步骤**，不是三个需要各自封装的函数：

```text
获取当前页 → 解析当前页 → 判断下一页
```

必要的复杂解析可以交给独立的数据处理能力，但取页、解析结果的业务判断及翻页控制仍在主函数中按执行顺序可见。

### 单 Page 过程式示例

```python
def prepare():
    """导出并合并两个地区的库存数据。"""
    page = get_page()
    for region in regions:
        # 切换地区并确认页面就绪
        ...

        # 打开任务中心，记录已有任务
        ...

        # 发起导出，等待本轮任务完成并下载
        ...

    # 校验并合并下载结果
    ...
    return result
```

上述页面动作直接放在 `prepare()`；复杂动态日期筛选、返回可用页面或独立数据处理等才按需使用辅助函数。示例只说明结构，不代表可运行的影刀 API。

### 独立能力示例

例如 `_get_page(url)` 内部负责根据 URL 获取或复用页面、检查并恢复登录状态、确认业务依赖的 JavaScript 已加载，最后返回可用于后续操作的 `page`。调用方只关心结果。

```text
page = _get_page(url)
继续执行页面业务
```

这个函数提供完整后置条件——“得到可直接工作的页面”，封装价值来自结果与职责，而非代码长度。

## 5. 直白与可读

- 变量名直白表达业务含义，避免 `x`、`tmp`、`obj` 等无语义名称。
- 新增函数或方法时，在函数体开头添加简短的 Sphinx / reStructuredText 文档注释。第一句直接说明这个函数“做什么”；有参数时使用 `:param 参数名: 含义`，有明确返回值时使用 `:return:` 说明返回结果。文档注释只描述职责、参数和返回结果，不展开内部执行步骤；未修改的历史函数不要求为了补文档批量整改。

```python
def get_page(url):
    """
    获取并返回可直接用于业务操作的页面。

    :param url: 目标页面地址
    :return: 已完成必要检查的页面对象
    """
```

### 业务步骤注释

- 注释粒度是“业务步骤”，不是“代码行”。函数体内按真实业务顺序分段，在每个主要业务步骤前放一行简短中文注释，让登录、进页、读取、扫描、计算、提交、校验、写回、保存、通知等步骤可以快速扫读。
- 一个连续代码块如果只完成同一个业务动作，只写一次步骤注释；注释说明业务意图，不复述 `goto`、`wait`、`find`、赋值、判断、日志等代码字面动作。
- 普通 `xbot` / 影刀 API 不因为是 API 就要求单独注释，例如 `page.goto(...)`、`page.find_by_xpath(...)`、`web.get(...)` 本身无需逐调用说明。市场指令是例外，仍按下一节的“功能 + 参数说明”规则执行。

```text
# 进入业务页面
page.goto(url)
page.wait_load()

# 扫描当前页待处理记录
rows = page.find_all(...)

# 计算并提交业务结果
result = ...
...
```

### 市场指令调用注释

所有市场指令调用都适用本规则，包括 Flow 的 `processN(...)`、直接 Python API，以及通过别名导入后的调用。市场指令的模块名、函数名和 `processN(...)` 往往不能完整表达真实业务含义，因此每个调用点都要用紧邻注释补足“功能 + 参数”。即使使用了关键字参数，也不能只依赖参数名让读者反推该市场指令做什么。

注释保持简短，至少包含：

- 该市场指令入口实际完成什么业务动作。
- 本次传入的每个参数分别控制什么；位置参数尤其要写清参数顺序。
- 说明以对应市场指令正式事实页或用户已确认用法为准，不根据 `processN` 编号或项目安装副本猜测；事实页缺少所需内容时说明缺口。

```text
注释格式示意（具体功能、参数名和顺序必须查对应事实页）：
# 某市场指令 processN：说明该入口实际完成的业务动作；参数依次说明每个位置参数的业务含义。
result = activity_xxx.processN(value_a, value_b)

# 使用关键字参数时，也要说明入口功能以及每个参数控制什么，不能只让读者根据参数名自行猜测。
result = activity_xxx.processN(option_a=value_a, option_b=value_b)
```

## 6. 异常、收尾与日志

- 捕获后只是继续失败时直接 `raise`；需要增加业务步骤、字段、XPath、订单号等定位信息时，使用 `raise ... from exc` 保留异常链。不要做 `raise RuntimeError(str(exc)) from exc` 这类无意义包装，也不要默认用 `raise ... from None` 隐藏底层异常。
- 如果一组顺序业务调用仅为出错日志而反复设置 `current_step = "..." `，通常无需单独维护它：在数据源写入、国家销量计算等最接近失败的位置补充 Sheet 名和业务动作，再由外层统一记录异常链。业务步骤确实驱动恢复、重试或停止决策时，仍应显式维护对应状态。
- `traceback.format_exc()` 和 `raise ... from exc` 不是替代关系：前者只把当前 `except` 中的完整异常现场转成文本，用于日志、通知或留痕；后者负责给异常增加业务上下文并继续向上抛。异常会继续向上抛且上层会统一记录完整堆栈时，中间层默认只传播异常，不重复记录 `traceback.format_exc()`，避免同一 traceback 在多层重复输出。
- 当前层会吞掉异常并继续下一个业务项、进入重试、发送失败通知，或需要在继续执行前保留现场时，才在当前 `except` 中记录 `traceback.format_exc()`。只在正在处理异常的 `except` 中使用它，不把返回的字符串当异常对象保存、传递或重新抛出。
- 正常路径直接执行关闭页面、工作簿、窗口、监听等收尾动作，让收尾失败正常抛出。
- 异常路径需要继续完成多个必要收尾时，在原 `except` 中分别记录收尾失败，完成后用裸 `raise` 重抛原业务异常，不让后续收尾异常覆盖主异常。

```text
非执行结构说明（不可直接运行）：
try:
    执行主业务
except Exception:
    logging.error(f"主业务失败：\n{traceback.format_exc()}")
    try:
        关闭工作簿
    except Exception:
        logging.error(f"关闭工作簿失败：\n{traceback.format_exc()}")
    try:
        关闭页面
    except Exception:
        logging.error(f"关闭页面失败：\n{traceback.format_exc()}")
    raise
else:
    关闭工作簿
    关闭页面
```

- 显式重试在每次尝试开始时记录次数和必要上下文，失败时记录完整堆栈；最终一次失败在对应的 `except` 中直接 `raise`，需要增加业务上下文时使用 `raise ... from exc`，不要把异常保存到变量后脱离原 `except` 再重新抛出。
- 正常业务 API 已能明确抛错时，直接依赖该失败，不增加等价的前置校验、全量预检、重复读取或多套兜底逻辑。

### 业务过程可追踪日志

日志首先服务于运行过程还原和故障定位，而不是追求数量。一次任务执行结束后，仅查看日志应当基本能够回答：当前执行到了哪个主要业务阶段、正在处理哪个平台 / 店铺 / 业务对象、对象发生了什么、为什么继续 / 停止 / 跳过 / 重试、程序采取了什么恢复动作、最终业务结果是什么，以及出错时失败在哪个步骤。

- 关键阶段按真实流程选择，例如任务开始、平台 / 店铺开始、登录状态、进入核心业务页面、开始扫描或处理、翻页 / 批次变化、停止原因、店铺完成和任务结束；不要求机械记录每个简单动作。
- 商品、订单、任务等业务对象的日志带上能够稳定定位对象的最小字段。例如库存业务可能使用平台、店铺、商品 ID、SKU；订单业务可能使用平台、店铺、订单号。字段由业务决定，不固定要求商品标题等无助于定位的信息。
- 同一业务持续输出多条日志时，推荐保持稳定、易扫读的上下文顺序，例如 `【业务】平台｜业务对象：发生了什么`；系统级日志可使用 `【系统】模块：发生了什么`。具体标点和字段可按项目调整，但同类日志的业务、平台、对象和事件顺序应尽量一致，方便连续阅读和检索。
- 会改变程序执行路径的判断具有独立排查价值，应记录决定及原因。不要只记录“停止”“跳过”“重试”，而要让日志能够说明为什么作出该决定。
- 自动恢复、重试、重建、降级等异常路径，日志不仅记录失败原因，还应说明程序随后采取的恢复动作。例如页面失效后准备重新建页、第一次执行失败后准备完整重试。避免把“失败”和“正在恢复”拆成缺少上下文、彼此难以关联的模糊日志。
- 对定时轮询、延迟重试、周期任务等长期运行流程，如果本次业务结果会决定下一次执行时间，结果日志应同时说明下一步动作或等待时长。例如“本轮不处理，10 分钟后再次检查”，使日志能够解释程序当前为什么没有继续操作。
- 最终结果优先记录实际发生的业务事实，而不是笼统写“处理成功”。例如库存业务可记录 `库存=0→20｜增加=20`；跳过时说明跳过原因；失败时说明业务步骤和异常原因，需要当前层保留现场时继续按本节异常规则记录 `traceback.format_exc()`。
- 业务异常和异常通知属于两个不同结果，应能够分别追踪。发生异常后，如项目存在通知机制，日志应能够区分未达到通知条件、被限频抑制、通知已发送、通知发送失败等状态；通知自身失败不得覆盖或模糊原始业务异常。
- 过程可追踪不等于每个动作都打日志。同一对象在极短时间内连续出现的“发现 → 开始 → 完成”若没有独立排查意义，可以只保留最终结果；只有操作耗时较长、容易卡住、存在多个关键阶段或需要观察重试过程时，才额外记录开始或阶段日志。简单赋值、普通 `find`、`click`、`goto`、字段读取以及紧邻的内部转换通常不单独记录日志。

```text
【拼多多】BOW官方旗舰店：库存更新成功｜商品ID=977725329892｜SKU=...｜库存=0→20｜增加=20
【弹卡】抖音｜直播间A：页面激活失败，清理残留页面后重新建页；原因=页面对象已失效
【福袋发布】抖音｜直播间A：已有活动进行中，本轮不发布；10 分钟后再次检查
【弹卡】抖音｜直播间A：异常仍在持续，但 1 小时内已发送过异常通知，本次不重复发送
```

以上具体平台、字段、时间、阈值和恢复动作只用于展示推荐的日志形态，不构成通用业务规则。实际项目中的刷新周期、重试次数、通知阈值、限频时间和页面恢复策略仍由各项目自己的业务规则决定。

#### 日志对象的使用边界

当业务代码持续重复平台、店铺、任务等稳定上下文，商品 ID / SKU / 订单号等对象字段格式，日志级别、字段顺序、分隔格式或 traceback 拼接时，可以主动提取日志格式函数或专门日志对象。日志封装有实际价值时直接使用，不需要为了保持业务代码表面上的“直接”而重复拼接日志字符串。

日志对象不要求只能有一两个方法。只要职责仍然明确属于“怎么记录”，可以按项目真实需求提供流程日志、商品日志、订单日志、异常日志等能力，并统一稳定上下文、字段格式、日志级别和异常输出，不需要为了追求极小接口而反复在业务代码中拼接日志字符串。

但日志对象不得承担决定程序行为的业务状态和决策。当前页码、当前步骤、停止原因、重试次数、是否继续翻页、是否达到停止条件、连续命中次数、待处理 / 待重试集合等仍由业务代码显式维护。**拿掉日志输出后，如果这个状态或判断仍会改变程序的执行结果，它就是业务逻辑，不属于日志对象。**

原则：**业务流程保持直接，独立能力按功能边界封装；日志基础设施按需要封装；业务过程显式，日志格式隐藏；日志对象负责怎么记录，业务代码负责怎么执行。**
