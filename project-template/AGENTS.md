# AGENTS.md

本文件用于真实影刀 xbot / 编码版项目，只保留执行任务时必须常驻的约束。详细示例和 API 事实仍以用户提供的知识库为准，不在项目内复制第二套文档。

## 需求理解与合理性判断

1. 用户对业务目标、处理范围、验收标准和最终取舍有决定权，但用户描述的技术事实、原因判断和实现方案不因此自动成立。规则优先级决定采用谁的业务决策，不用于替代对代码、API 和运行事实的核验。
2. 用户目标清楚、正确方案唯一且不改变业务口径时，可以按最小正确方案继续执行并说明判断。若不同方案会改变业务结果、数据口径、风险承担或长期规则，应把关键分歧交给用户决定，不替用户擅自选择。

## 开始任务

1. 业务规则优先级：**用户明确确认的业务目标、范围、验收标准和取舍决定 > 当前项目正式 PRD / 规范 > 当前代码与既有业务约定 > 历史经验**。影刀 xbot API 和市场指令的调用事实以知识库正式页面为准。用户明确确认的业务决策与 PRD / 规范冲突时，以用户当前决定为准；若该决定改变长期业务规则，应同步更新对应正式文档。
2. 当用户明确要求优化、重构或规范代码时，不要因为“当前代码原本就是这样写的”而保留不合理的结构、代码风格或实现方式；应在不改变已确认业务规则、数据口径和外部接口的前提下，按知识库中的开发规则进行调整。只修改用户要求优化的范围，不顺带重构无关代码。
3. 用户明确确认的业务规则、字段名、路径、Sheet 名等项目专有事实视为已确认输入。开发时参考当前项目已有的相同或相近业务实现；涉及影刀 API 或市场指令调用时先按知识库正式页面确认用法。修改或新增代码时，如需判断同类实现是否保持一致，使用 `.agents/skills/code-consistency/SKILL.md`；完成非简单代码改动后需要进一步简化本次实现时，使用 `.agents/skills/code-simplifier/SKILL.md`；用户要求代码审查，或重要改动需要独立检查正确性时，使用 `.agents/skills/code-review/SKILL.md`。
4. 只改与需求直接相关的内容，不做无关重构、格式化或结构调整；先读相关代码并保留用户已有改动。
5. 知识库固定路径为 `C:\Users\Administrator\Desktop\影刀xAI开发指南`。涉及影刀 API、市场指令或跨项目开发知识时，按下方“xbot 与知识库”的检索顺序查询；目录不存在时立即停止，并要求用户提供正确路径，不自行猜测其它位置。

## 项目分析与执行边界

1. **项目自身的问题，直接分析真实项目。** 查找项目配置来源、数据源、业务接口、字段、调用链和现有业务行为时，读相关代码和规范，不通过 ShadowBot CLI 的运行时接口绕行获取；影刀 API 与市场指令的调用事实按下方知识库规则查询。
2. **ShadowBot CLI 只承担 ShadowBot 自身的应用生命周期和运行时能力。** 应用搜索 / App ID、Studio 保存同步、发布、Console 任务、任务日志、运行状态、影刀设置等场景按对应 Skill 使用 CLI；普通源码分析、代码修改和项目内脚本执行不依赖 CLI。
3. **分析外部数据源时先静态追踪，再做最小请求验证。** 从源码确认真实连接方式、Base / Sheet / API 和字段后，可复用项目已有依赖与运行环境编写最小临时脚本直接请求数据源；数据迁移通过源端读取 / 导出和目标端写入完成，不通过运行完整 RPA 流程搬运数据。
4. **不得为了“看看运行时变量 / 配置 / Sheet / 店铺列表是什么”而启动影刀应用或主流程。** 应用或任务运行属于真实业务执行，不是只读检查。只有用户明确要求运行时才执行；运行前仍需确认数据范围和副作用。
5. 临时脚本需要凭据时，应让脚本在进程内从项目现有配置读取并直接完成请求；不要把密码、Token、Cookie、Secret 等打印到终端、聊天或中间文件。临时排查文件完成后删除，除非用户明确要求保留。

## 代码结构与编程风格

本节是业务代码的硬约束，不因详细示例放在知识库中而减弱。

“代码简单”指让真实业务顺序直接可见，并让每一层代码只暴露该层需要理解的概念，减少不必要的状态、中间变量和函数跳转。只调用一次、只服务当前业务流程的读取、校验、判断、计算、写回等步骤，默认就地表达；不要仅为了给代码起名字、缩短 `main()`、分层或区分“数据层 / 业务层”而提取函数。单次调用不是绝对禁止封装：只有能力本身具有独立职责，调用方只需要结果、不需要理解内部步骤，且封装确实隐藏了一组实现细节时，才值得提取。

1. 自动化和数据处理默认使用自上而下的过程式主流程，让读取、判断、操作、写回、保存和通知顺序直接可见；业务步骤有明确先后时，代码保持同样顺序。
2. `run.py` 保留 `main(args)` 影刀入口和主业务顺序；业务配置统一在 `config.py` 定义，由使用它的模块直接导入，不把影刀运行参数作为默认配置来源；已有 `tool.py`、`utils.py`、`win_utils.py` 只承载真正独立或稳定复用的能力。
3. 单次使用的 URL、XPath、CSS、字段名、按钮文案、状态值、简单属性、简单表达式和立即调用结果，默认在使用位置内联。只有需要复用、后续判断、表达式较复杂、命名能解释业务含义，或必须保留对象状态时才提取变量。只为紧接着调用一次方法、读取一次属性或继续一次简单转换而创建的中间变量，视为无意义临时变量，应直接链式表达；不要把 `find → click`、`find → get_text`、`get_text → strip` 这类一次性连续操作人为拆成多个变量。
4. 单次调用且属于当前业务流程的简单读取、校验、判断、计算、写回等步骤默认不拆；不要仅为了给代码起名字、缩短当前函数或形式分层而提取函数。不要把“职责单一”“有输入输出”“数据能力”本身当作拆函数理由。当一段逻辑本身构成完整业务阶段，提取后能让调用方直接看到更高层的业务顺序，并且调用方不需要理解该阶段内部步骤时，可以提取为中层函数；是否提取看业务边界，不看代码行数或调用次数。不要继续把一个完整业务阶段拆成多个只包装简单读取、判断、转换或写回的小函数。真正独立能力也可以提取，例如 `_get_page(url)` 内部完成获取 / 复用页面、恢复登录、等待页面就绪，最后只返回可直接使用的 `page`。只包一两个调用、简单字段转换、读一行再组字典，或只是把当前流程换个函数名继续调用的逻辑，默认就地表达。简单赋值不要先初始化一个占位值，再用紧接着的短 `if` 覆盖同一变量；若结果只是简单二选一，且条件表达式仍清晰，应直接一次赋值。只有分支包含多个业务动作、异常处理、副作用，或条件表达式明显降低可读性时才展开 `if`。
5. 函数只接收实际需要的具体值；只使用字典中少数字段时，不传整个 `dict` 或巨型 `context`。状态只保留跨步骤确实需要共享的部分。稳定且不会在本次运行中被动态覆盖的项目级配置，若目标模块可直接从 `config.py` 导入，则由实际使用它的模块直接导入，不要先在 `run.py` 读取后再仅为传递配置而跨多层函数转发；函数参数主要承载运行时变化的业务数据。通用底层函数可以继续接收路径、连接信息等参数，由最近的业务模块传入。
6. 查询、读取、接口封装等数据获取层默认返回实际结果；查询到 `0 / 1 / N` 条、空列表或空结果在当前业务中应失败、跳过还是继续，由实际业务调用方判断。数据获取层仍负责自身技术契约和技术异常，例如 SQL / 请求失败、返回结构无法解析或文件格式损坏；不要把某个调用方特有的业务规则下沉进去。
7. 是否使用类按对象边界判断，不做“普通业务默认不用类”的全局限制。多个操作如果天然围绕同一对象、共享必要状态或生命周期，并且类可以向调用方提供稳定、清楚的结果接口，就可以使用；如果只是把几个无状态函数放进类里分组，或只有一两步简单操作，则不必为了形式使用类。日志等辅助基础设施同样按这一标准判断。
8. 业务代码不新增无必要的 Service、Manager、Context、Registry、Factory、Dispatcher、Strategy 或大型配置层；不为未来需求预留 Hook、兼容层或扩展点。RPA 只实现当前确定需要的运行方式，不为了以后可能调试或补跑而默认加入强制执行、任务范围选择等开关和分支；已确认的业务安全措施与实际故障保护仍应保留。该约束针对承载或控制业务逻辑的抽象层，不针对职责明确的日志等辅助基础设施；是否合理以实际职责判断，不根据类名机械判断。
9. 函数和方法调用在保持可读时优先写在一行；参数很多或结构复杂时正常换行，不为了“一行”损害可读性。字典、列表等数据结构按其结构正常换行。变量名直白表达业务含义。新增函数或方法时，在函数体开头添加简短的 Sphinx / reStructuredText 文档注释，先说明这个函数“做什么”；有参数时使用 `:param 参数名: 含义`，有明确返回值时使用 `:return:` 说明返回结果。文档保持简短，不复述内部实现步骤；未修改的历史函数不要求为了补文档批量整改。
10. 函数体内按真实业务步骤分段，并在每个主要业务步骤前添加一行简短中文注释，使登录、进页、读取、扫描、计算、提交、校验、写回、保存、通知等步骤能够快速扫读。注释说明业务意图，不逐行复述代码；普通影刀 API 调用、简单赋值、显而易见的判断和日志语句无需单独加注释。市场指令仍按“功能 + 参数说明”的专项规则执行。
11. `main(args)` 是影刀调用 Code 流时的入口约定，不要求其他 Python 文件都定义它。模块之间按正常 Python 语法导入和调用，函数只接收实际需要的业务数据；只有明确需要对接已有流程参数的项目，才在 `main(args)` 边界读取对应字段。
12. 异常处理只覆盖明确需要处理的失败，不静默吞错。直接继续失败时使用 `raise`；补充业务上下文时使用 `raise ... from exc`；`traceback.format_exc()` 用于记录异常现场，`raise` / `raise ... from exc` 用于异常传播，上层会统一记录完整堆栈时中间层不重复记录；异常路径的收尾不得覆盖原业务异常。
13. 健壮性只处理真实可能且业务明确要求处理的失败。正常业务 API 已能明确抛错时，直接依赖该失败，不增加等价的前置校验、全量预检、重复读取或多套兜底逻辑。
14. 业务日志应能够还原主要执行过程：记录关键业务阶段、影响流程走向的判断及原因、重要业务对象的最终结果，以及必要的异常现场。停止、跳过、重试等会改变执行路径的行为应说明原因；商品、订单、任务等对象日志带上定位所需的最小稳定上下文；成功日志尽量描述实际发生的结果，不只写“成功”。不要给简单赋值、普通 API 调用或没有独立排查价值的连续动作逐条打日志。
15. `step`、页码、停止原因、重试次数、连续命中次数、待重试集合等决定程序行为的业务状态继续由业务代码显式维护。多处持续重复日志上下文和格式时，应考虑提取日志格式函数或专门日志对象，统一稳定上下文、字段顺序、日志级别和异常输出；日志对象可以按实际需要增强日志能力，但只负责“怎么记录”，不得承担停止判断、重试决策、翻页逻辑等“怎么执行”的业务控制。原则：**业务过程显式，日志格式隐藏；日志对象负责怎么记录，业务代码负责怎么执行。**

需要查看变量内联、函数边界、异常收尾和业务过程日志的完整判断与示例时，读取知识库 `docs/coding-style.md`；以上规则已足以约束普通小改。

## xbot 与知识库

1. 不根据通用 Python 经验、旧项目记忆或名称相似度猜 xbot API、市场指令、页面字段、XPath 或命令。
2. 影刀 API 和市场指令的入口、参数、返回值及用法先查知识库正式事实页；项目现有代码只用于确认业务调用位置、数据来源和项目约定。安装副本或历史调用与正式页面不一致时，不据此改写知识库调用方式。
3. 进入知识库检索后，先读取知识库 `llms.txt`。如果 `llms.txt` 已能明确定位正式知识页，直接读取该页面；只有 `llms.txt` 无法明确定位时，才使用 QMD 作为 fallback 搜索候选知识。精确 API、函数名、文件名、报错文本、独特技术词等优先只做 lexical 查询，并关闭 rerank；只有纯 lexical 无法稳定定位时，再加入 vector / hyde 查询。语义查询时限制候选数量，避免无意义的大范围重排。QMD 返回的 snippet 只用于定位候选文档，必须继续使用 `get` / `multi_get` 读取完整正式原文后再实现。
4. QMD 的 Collection 只表示知识层身份，不是自动覆盖规则。涉及 API、市场指令、参数、返回值和已核验行为时，以 `yingdao-api` 正式事实为优先；跨 API 稳定开发知识使用 `yingdao-docs`；`yingdao-skills` 只在对应专项任务触发时使用；`yingdao-reference` 仅用于参考真实项目落地方式，不得覆盖 AGENTS、正式 API 事实或 docs 正式知识。
5. 调用任何市场指令（`xbot_extensions`）时，无论是 Flow 的 `processN(...)`、直接 Python API，还是通过别名导入后调用，都必须在调用点紧邻添加注释，至少说明该入口的业务功能，以及本次传入各参数的名称和含义；不得只保留裸调用。功能和参数说明以知识库正式事实页或用户已确认用法为准，不得根据函数编号、函数名、参数值或安装副本猜测。知识页缺少所需事实时说明缺口；不为日常调用自动转查源码。
6. 知识页已有入口而项目导入失败或缺少模块时，先提示检查、更新或重新安装对应市场指令。若市场尚无包含该入口的版本，明确说明发布缺口；只有用户要求排查版本差异或升级后仍异常时，才检查安装副本。
7. 网页相关问题查 `browser.md`，Win32 查 `win32.md`，Excel / WPS 查 `excel.md`；不机械加载与当前改动无关的全文。
8. 网页业务默认使用 `xbot.web`；等待明确异步条件，不靠不断增加固定 `sleep`。
9. 影刀日志使用 `from xbot.app import logging`；动态内容使用完整 f-string，异常堆栈使用 `traceback.format_exc()`。
10. 读取 / 迁移旧版可视化项目，或排查“应用文件已损坏”、flow 文件缺失、`package.sigstore` 等项目级问题时，使用 `.agents/skills/xbot-project-diagnostics/SKILL.md`；普通 Python 业务 bug 不触发。
11. `selectorsV2.xml` 是由影刀编辑器维护的元素库文件，Agent 不得创建、编辑、格式化、覆盖或补丁修改该文件，否则影刀编辑器会提示应用文件损坏。需要调整元素库时应通过影刀编辑器操作；业务代码只读取并使用项目中已有的元素库名称。
12. 单项 CLI 操作读取 `.agents/skills/shadowbot-cli/SKILL.md`；使用 CLI 完成应用创建、开发、发布和试运行的完整流程时读取 `.agents/skills/xbot-app-lifecycle/SKILL.md`。命令和参数以本机 CLI 帮助及实际返回为准。

## 验证与同步

1. 按风险做最小必要验证；默认不新增测试或运行无关全量检查。高风险写入先确认范围和回退方式。
2. Code flow 同步 helper 属于 `.agents/skills/xbot-app-lifecycle/scripts/sync_codeflows.py`，不再作为项目根目录的独立工具。只有新增或删除项目根目录 `.py` 文件时才运行；新增文件会登记对应 Code flow，删除文件会移除对应 Code flow 注册。只修改已有 `.py` 文件时不要运行 Code flow 同步 helper。新增 `.py` 的文件名去扩展名后不得与 `package.json` 中已有 flow 的 `name` 重复，例如已有名为 `init` 的 Visual flow 时不能新建 `init.py`；撞名登记后 Studio 打开项目会直接报“应用文件已损坏”，排查与修复见 `xbot-project-diagnostics`。
3. 用户明确要求发布外部修改后的影刀应用时，优先运行 `.agents/skills/xbot-app-lifecycle/scripts/publish_app.py`。它负责打开已有应用、重新载入磁盘修改、保存编译、同步、发布并校验线上 `versionId` 已变化；不要手工拆成多条 CLI 命令，也不要仅凭 `console app publish` 返回成功就认定新代码已上线。新增 / 删除 `.py` 时先单独运行 `sync_codeflows.py`，普通已有文件修改直接发布即可。
4. 同步 helper 自动扫描项目根目录 Python 文件并同步 Code flow 注册，不接收文件列表或 `prepare` 子命令；它是 `xbot-app-lifecycle` 的内部确定性步骤，不是 Git 操作，成功也不等于影刀编辑器内保存、同步或运行验证。
5. 验证失败时先区分代码、环境、依赖和路径问题，不为通过无关检查扩大改动。
6. 用户说 'push' 时指的是 git commit 并 push 到 GitHub / Gitee 远程仓库。执行前确认有改动需要提交，并使用清晰的 commit 信息。

## 安全与汇报
