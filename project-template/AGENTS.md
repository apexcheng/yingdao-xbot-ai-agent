# AGENTS.md

本文件用于真实影刀 xbot / 编码版项目，只保留执行任务时必须常驻的约束。详细示例和 API 事实仍以用户提供的知识库为准，不在项目内复制第二套文档。

## 需求理解与合理性判断

1. 用户对业务目标、处理范围、验收标准和最终取舍有决定权，但用户描述的技术事实、原因判断和实现方案不因此自动成立。规则优先级决定采用谁的业务决策，不用于替代对代码、API 和运行事实的核验。
2. 用户目标清楚、正确方案唯一且不改变业务口径时，可以按最小正确方案继续执行并说明判断。若不同方案会改变业务结果、数据口径、风险承担或长期规则，应把关键分歧交给用户决定，不替用户擅自选择。

## 开始任务

1. 业务规则优先级：**用户明确确认的业务目标、范围、验收标准和取舍决定 > 当前项目正式 PRD / 规范 > 当前代码与既有业务约定 > 历史经验**。用户明确确认的业务决策与 PRD / 规范冲突时，以用户当前决定为准；若该决定改变长期业务规则，应同步更新对应正式文档。
2. 用户明确确认的业务规则、字段名、路径、Sheet 名等项目专有事实视为已确认输入。优先参考当前项目已有的同类实现。需要一致性检查、非简单改动的进一步简化，或用户要求代码审查时，按任务目的使用 `.agents/skills/code-quality/SKILL.md` 对应部分；只读审查不得自动修改文件。
3. 只改与需求直接相关的内容，不做无关重构、格式化或结构调整；先读相关代码并保留用户已有改动。
4. 知识库固定路径为 `C:\Users\Administrator\Desktop\影刀xAI开发指南`。需要检索影刀知识时按下方“xbot 与知识库”的顺序查询；目录不存在时立即停止并要求用户提供正确路径。

## 项目分析与执行边界

1. **项目自身的问题直接分析真实项目。** 配置、数据源、业务接口、字段、调用链和当前行为从代码与规范确认；ShadowBot CLI 仅用于应用搜索 / App ID、Studio、发布、Console 任务、日志、运行状态和影刀设置等自身生命周期及运行时操作，不能替代普通源码分析或项目内脚本。
2. **分析外部数据源时先静态追踪，再做最小请求验证。** 从源码确认真实连接方式、Base / Sheet / API 和字段后，可复用项目已有依赖与运行环境编写最小临时脚本直接请求数据源；数据迁移通过源端读取 / 导出和目标端写入完成，不通过运行完整 RPA 流程搬运数据。
3. **不得为了“看看运行时变量 / 配置 / Sheet / 店铺列表是什么”而启动影刀应用或主流程。** 应用或任务运行属于真实业务执行，不是只读检查。只有用户明确要求运行时才执行；运行前仍需确认数据范围和副作用。
4. 临时脚本需要凭据时，应让脚本在进程内从项目现有配置读取并直接完成请求；不要把密码、Token、Cookie、Secret 等打印到终端、聊天或中间文件。临时排查文件完成后删除，除非用户明确要求保留。

## 代码结构与编程风格

本节是业务代码的硬约束，不因详细示例放在知识库中而减弱。

1. 自动化和数据处理默认使用自上而下的过程式主流程，让读取、判断、操作、写回、保存和通知顺序直接可见；**固定的业务任务按顺序直接调用**，不要为了统一保存、异常或状态处理，把固定调用改成配置元组、任务列表加循环。公共处理细节可放在被调用函数中；只有任务集合实际动态变化或需要同一规则批量遍历时才使用循环。
2. `run.py` 保留影刀 Code 流入口 `main(args)` 和主业务顺序；其他 Python 文件正常导入调用，不必定义 `main(args)`。业务配置在 `config.py` 定义，由使用它的模块直接导入，不把运行参数当作默认配置来源；已有 `tool.py`、`utils.py`、`win_utils.py` 只放独立或稳定复用的能力。共享工作簿的打开、传递和最终关闭在主流程直接可见；业务 WPS 工作簿使用 `xbot.excel.open(file_name=str(target), kind="wps", visible=True, update_links=False)`，统一或逐任务保存由业务要求决定。写入失败按项目要求中断或处理，不默认增加丢弃未保存内容并重开工作簿的恢复函数。
3. 单次使用的 URL、XPath、CSS、字段名、状态值、简单表达式和立即调用结果默认在使用位置内联；XPath 一律在使用位置内联，并写成单个单行字符串，不换行拆分、不用隐式字符串拼接，便于用户直接复制核实；即使多处复用也不提取为模块常量、局部变量或拼接前缀。`find → click`、`get_text → strip` 等一次性连续操作不人为拆中间变量。需要复用、后续判断、明确解释业务含义或保留对象状态时可以提取变量（XPath 除外）。简单二选一结果能清楚表达时直接赋值，不先占位再用短 `if` 覆盖；有多个业务动作、副作用或异常处理时保留显式分支。
4. **单 Page 过程式编程。** 一个 Page 的业务操作默认由一个主函数负责，按实际执行顺序自上而下编写；页面切换、元素查找、筛选、点击、任务中心、导出、下载、等待及结果判断等步骤直接写在主函数中，不分别拆函数。多个地区或店铺在同一 Page 执行相同流程时，直接在主函数内循环。复杂且独立的能力（如动态日期筛选）、登录并返回可用 Page、实际跨业务复用的工具及独立数据处理可以封装；同一 Page 的普通操作即使重复使用，也不因此拆分。不按代码行数、单一职责或为了缩短主函数而封装。
5. 函数只传实际需要的运行时数据，状态只保留跨步骤需要共享的部分；使用字典中少数字段时不传整个 `dict` 或巨型 `context`。稳定项目配置由使用它的业务模块直接从 `config.py` 导入；已被运行时输入覆盖的配置继续按实际值传递，通用底层函数按需接收具体参数。
6. 查询、读取和接口封装等数据获取层返回实际结果并处理自身的技术异常；空结果、匹配 `0 / 1 / N` 条应失败、跳过还是继续，由调用方按业务规则判断。
7. 是否使用类看对象职责：天然围绕同一对象、共享必要状态或生命周期、向调用方提供清楚接口时可以使用；不要只为分组无状态函数而建类，也不新增无必要的 Service、Manager、Context 等业务抽象层。日志等辅助设施按实际职责判断，不按类名机械禁止。不为未来需求预留 Hook、兼容层、调试或补跑开关；已有业务安全保护必须保留。
8. 函数和方法调用在保持可读时优先写在一行；参数很多或结构复杂时正常换行，不为了“一行”损害可读性。字典、列表等数据结构按其结构正常换行。变量名直白表达业务含义。新增函数或方法时，在函数体开头添加简短的 Sphinx / reStructuredText 文档注释，先说明这个函数“做什么”；有参数时使用 `:param 参数名: 含义`，有明确返回值时使用 `:return:` 说明返回结果。文档保持简短，不复述内部实现步骤；未修改的历史函数不要求为了补文档批量整改。
9. 异常处理只覆盖明确需要处理的失败，不静默吞错。直接继续失败时使用 `raise`；补充业务上下文时使用 `raise ... from exc`；`traceback.format_exc()` 用于记录异常现场，`raise` / `raise ... from exc` 用于异常传播，上层会统一记录完整堆栈时中间层不重复记录；异常路径的收尾不得覆盖原业务异常。
10. **禁止未经用户确认新增任何防御性代码。** 无论风险是真实存在还是仅为推测，都不得擅自增加防御性前置校验、重试、回退、兜底、预检、重复读取或额外状态。发现风险时只在回复末尾说明风险及影响，并询问用户是否需要增加相应防御；得到用户明确同意后才实施。现有保护和已确认的业务规则不得借此擅自删除；正常业务 API 能直接抛错时直接传播，不增加等价保护。
11. 决定执行路径的步骤、重试、停止条件等状态由业务代码维护；仅用于错误描述的信息直接在异常位置补充。多处日志格式或上下文重复时可以封装日志辅助，但不让日志对象决定业务流程。

需要查看变量内联、函数边界、异常收尾和日志对象的完整判断与示例时，读取知识库 `project-template/.agents/skills/code-quality/references/coding-style.md`；以上规则已足以约束普通小改。

## xbot 与知识库

1. 不根据通用 Python 经验、旧项目记忆或名称相似度猜 xbot API、市场指令、页面字段、XPath 或命令。项目已有相同、已确认的 API 用法且本次调用契约不变时直接参考，不重复查知识库；新增调用、改参数、返回值不确定、调用失败或现有用法有争议时，查正式 API / 市场指令事实页。项目安装副本或历史调用不能推翻正式 API 事实。
2. 需要检索时先通过知识库 `llms.txt` 直达正式页面；无法定位再用 QMD 搜索候选，精确术语优先 lexical，必要时语义检索。搜索摘要只用于定位，必须读完整正式原文；QMD Collection 和参考项目不覆盖正式 API / docs 或项目规则。
3. 调用任何市场指令（`xbot_extensions`）时，无论是 Flow 的 `processN(...)`、直接 Python API，还是通过别名导入后调用，都必须在调用点紧邻添加注释，至少说明该入口的业务功能，以及本次传入各参数的名称和含义；不得只保留裸调用。功能和参数说明以知识库正式事实页或用户已确认用法为准，不得根据函数编号、函数名、参数值或安装副本猜测。知识页缺少所需事实时说明缺口；不为日常调用自动转查源码。
4. 知识页已有入口而项目导入失败或缺少模块时，先提示检查、更新或重新安装对应市场指令。若市场尚无包含该入口的版本，明确说明发布缺口；只有用户要求排查版本差异或升级后仍异常时，才检查安装副本。
5. 网页相关问题查 `browser.md`，Win32 查 `win32.md`，Excel / WPS 查 `excel.md`；不机械加载与当前改动无关的全文。
6. 网页业务默认使用 `xbot.web`；所有 Page 新建、跳转、刷新等加载完成后，先 `page.wait_load_completed(...)`，再统一 `time.sleep(3)`，然后开始业务操作，避免 JS 仍在初始化。需要等待异步业务结果时仍须检查实际状态，不用不断叠加固定等待。
7. 影刀日志使用 `from xbot.app import logging`；动态内容使用完整 f-string，异常堆栈使用 `traceback.format_exc()`。
8. 读取 / 迁移旧版可视化项目，或排查“应用文件已损坏”、flow 文件缺失、`package.sigstore` 等项目级问题时，按需读取 `.agents/skills/xbot-tools/references/project-diagnostics.md`；普通 Python 业务 bug 不触发。
9. **严格禁止 Agent 直接修改 `selectorsV2.xml`**：不得创建、编辑、格式化、覆盖或补丁修改该文件。需要增删或调整元素库时，Agent 只能提示用户自行通过影刀编辑器修改，不得代替用户修改文件；业务代码只读取并使用项目中已有的元素库名称。
10. 单项 CLI 操作使用 `.agents/skills/xbot-tools/SKILL.md` 中「CLI 操作」部分；使用 CLI 完成应用创建、开发、发布和试运行的完整流程时使用其中「应用开发闭环」部分。命令和参数以本机 CLI 帮助及实际返回为准。
11. 跨轮次去重、状态与重试，多数据源 / 多 Sheet 报表、异步导出任务绑定、钉钉业务通知及跨层排错等专项任务，按需读取 `.agents/skills/rpa-practices/SKILL.md` 中对应经验与完整案例；简单项目改动不默认加载全部材料。

## 验证与同步

1. 按风险做最小必要验证；默认不新增测试或运行无关全量检查。高风险写入先确认范围和回退方式。
2. Code flow 同步 helper 属于 `.agents/skills/xbot-tools/scripts/sync_codeflows.py`，不再作为项目根目录的独立工具。只有新增或删除项目根目录 `.py` 文件时才运行；新增文件会登记对应 Code flow，删除文件会移除对应 Code flow 注册。只修改已有 `.py` 文件时不要运行 Code flow 同步 helper。新增 `.py` 的文件名去扩展名后不得与 `package.json` 中已有 flow 的 `name` 重复，例如已有名为 `init` 的 Visual flow 时不能新建 `init.py`；撞名登记后 Studio 打开项目会直接报“应用文件已损坏”，排查与修复见 `.agents/skills/xbot-tools/references/project-diagnostics.md`。
3. 验证失败时先区分代码、环境、依赖和路径问题，不为通过无关检查扩大改动。
4. 用户说 'push' 时指的是 git commit 并 push 到 GitHub / Gitee 远程仓库。执行前确认有改动需要提交，并使用清晰的 commit 信息。

## 安全与汇报

1. 不隐藏副作用，不通过吞异常、静默失败或模糊返回值让主流程看起来成功。
2. 不提交账号、密码、Token、Cookie、Webhook、客户数据或未公开地址；示例和日志必须脱敏。
3. 长期业务规则和设计决策写入项目已有正式文档。

正常回复用户内容。
