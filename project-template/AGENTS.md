# AGENTS.md

本文件用于真实影刀 xbot / 编码版项目，只保留执行任务时必须常驻的约束。详细示例和 API 事实仍以用户提供的知识库为准，不在项目内复制第二套文档。

核心原则：**最小改动、过程清楚、不猜 API、按风险验证。**

## 需求理解与合理性判断

1. 用户对业务目标、处理范围、验收标准和最终取舍有决定权，但用户描述的技术事实、原因判断和实现方案不因此自动成立。规则优先级决定采用谁的业务决策，不用于替代对代码、API 和运行事实的核验。
2. 不预设用户熟悉当前项目、调用链、数据结构或影刀 API。用户的表述可能是业务目标、现象描述、疑问、技术猜测或建议方案；修改前先识别用户真正想解决的问题，再结合当前代码、项目规范、知识库事实和必要的运行证据判断建议是否适用。
3. 执行技术建议前，至少判断它是否真正解决业务目标、是否符合当前代码及上下游调用契约、现有逻辑是否已经完成相同职责，以及是否会引入重复处理、行为变化、数据风险或不必要复杂度；同时区分用户指出的是根因还是局部现象。
4. 用户建议合理且与项目事实一致时直接执行。建议存在明显误解、重复实现或更高风险时，应先说明具体依据和影响，并给出满足原业务目标的最小正确方案，不机械照改，也不只以“用户要求如此”作为实现依据。
5. 用户目标清楚、正确方案唯一且不改变业务口径时，可以按最小正确方案继续执行并说明判断。若不同方案会改变业务结果、数据口径、风险承担或长期规则，应把关键分歧交给用户决定，不替用户擅自选择。
6. 对用户建议提出异议必须基于当前代码、正式文档、运行结果或可解释的调用关系，不以个人偏好、过度设计或抽象的“最佳实践”为理由扩大任务。

## 开始任务

1. 规则优先级：**用户明确确认的业务目标、范围、验收标准和取舍决定 > 当前项目正式 PRD / 规范 > 当前代码与既有业务约定 > 知识库与历史经验**。用户明确确认的业务决策与 PRD / 规范冲突时，以用户当前决定为准；若该决定改变长期业务规则，应同步更新对应正式文档。
2. 当用户明确要求优化、重构或规范代码时，不要因为“当前代码原本就是这样写的”而保留不合理的结构、代码风格或实现方式；应在不改变已确认业务规则、数据口径和外部接口的前提下，按知识库中的开发规则进行调整。只修改用户要求优化的范围，不顺带重构无关代码。
3. 用户明确确认的业务规则、字段名、路径、Sheet 名等项目专有事实视为已确认输入；当前代码中已验证的稳定 API 调用和 XPath 优先沿用。用户新提出的 API、参数、XPath 或实现方式仍按“需求理解与合理性判断”核验，不因由用户提出而直接视为技术事实。
4. 只改与需求直接相关的内容，不做无关重构、格式化或结构调整；先读相关代码并保留用户已有改动。
5. 目标清楚时直接执行。只有新增完整功能、跨模块影响主流程、涉及未确认外部行为或高风险操作时，才做简短的“计划 → 执行 → 验证”。
6. 知识库固定路径为 `C:\Users\Administrator\Desktop\影刀xAI开发指南`。知识库只补足项目无法确认的部分；需要查询 xbot API、市场指令、开发规范或排错资料时，优先检查该目录并按其中 `llms.txt` 路由。目录不存在时立即停止，并要求用户提供正确路径，不自行猜测其它位置。
7. 同一优先级或优先级未明确的规则发生冲突时，选择改动更小、结构更简单、业务顺序更清楚、风险更低的方案；不得用该原则覆盖前述明确优先级。

## 代码结构与编程风格

本节是业务代码的硬约束，不因详细示例放在知识库中而减弱。

“代码简单”指减少不必要的状态、中间变量、分支和层级，不是拒绝合理封装。是否封装主要看功能边界，而不是代码行数、实现复杂度或复用次数：一个能力如果职责单一、输入输出清楚、内部步骤共同保证一个明确结果，调用方只需要关心结果而不需要理解内部过程，就可以封装；只有一两行简单动作、紧邻使用且没有独立职责的逻辑，默认就地表达。

1. 自动化和数据处理默认使用自上而下的过程式主流程，让读取、判断、操作、写回、保存和通知顺序直接可见；业务步骤有明确先后时，代码保持同样顺序。
2. `run.py` 保留 `main(args)` 入口和主业务顺序；`config.py` 只放项目配置、配置路径或稳定静态设置；稳定且真正复用的能力沿用已有 `tool.py`、`utils.py`、`win_utils.py`，不为整理代码另建工具层。
3. 单次使用的 URL、XPath、CSS、字段名、按钮文案、状态值、简单属性、简单表达式和立即调用结果，默认在使用位置内联。只有需要复用、后续判断、表达式较复杂、命名能解释业务含义，或必须保留对象状态时才提取变量。只为紧接着调用一次方法、读取一次属性或继续一次简单转换而创建的中间变量，视为无意义临时变量，应直接链式表达；不要把 `find → click`、`find → get_text`、`get_text → strip` 这类一次性连续操作人为拆成多个变量。
4. 函数和模块封装优先按功能边界判断，不按代码长短或复杂度判断。职责单一、输入输出明确、内部细节可以被调用方忽略的独立能力可以提取，即使当前只调用一次；重复使用只是额外理由，不是前提。反之，只包一两行简单动作、只是给代码起名字、或封装后调用方仍必须了解并操纵内部步骤的逻辑，默认就地表达。简单赋值不要先初始化一个占位值，再用紧接着的短 `if` 覆盖同一变量；若结果只是简单二选一，且条件表达式仍清晰，应直接一次赋值。只有分支包含多个业务动作、异常处理、副作用，或条件表达式明显降低可读性时才展开 `if`。
5. 函数只接收实际需要的具体值；只使用字典中少数字段时，不传整个 `dict` 或巨型 `context`。状态只保留跨步骤确实需要共享的部分。稳定且不会在本次运行中被动态覆盖的项目级配置，若目标模块可直接从 `config.py` 导入，则由实际使用它的模块直接导入，不要先在 `run.py` 读取后再仅为传递配置而跨多层函数转发；函数参数主要承载运行时变化的业务数据。通用底层函数可以继续接收路径、连接信息等参数，由最近的业务模块传入。
6. 查询、读取、接口封装等数据获取层默认返回实际结果；查询到 `0 / 1 / N` 条、空列表或空结果在当前业务中应失败、跳过还是继续，由实际业务调用方判断。数据获取层仍负责自身技术契约和技术异常，例如 SQL / 请求失败、返回结构无法解析或文件格式损坏；不要把某个调用方特有的业务规则下沉进去。
7. 是否使用类按对象边界判断，不做“普通业务默认不用类”的全局限制。多个操作如果天然围绕同一对象、共享必要状态或生命周期，并且类可以向调用方提供稳定、清楚的结果接口，就可以使用；如果只是把几个无状态函数放进类里分组，或只有一两步简单操作，则不必为了形式使用类。日志等辅助基础设施同样按这一标准判断。
8. 业务代码不新增无必要的 Service、Manager、Context、Registry、Factory、Dispatcher、Strategy 或大型配置层；不为未来需求预留 Hook、兼容层或扩展点。该约束针对承载或控制业务逻辑的抽象层，不针对职责明确的日志等辅助基础设施；是否合理以实际职责判断，不根据类名机械判断。
9. 函数和方法调用一律写在一行，不因参数很多或结构复杂而换行；字典、列表等数据结构本身仍按其结构正常换行。变量名直白表达业务含义；需要函数文档注释时使用 Sphinx / reStructuredText 格式。
10. 函数体内按真实业务步骤分段，并在每个主要业务步骤前添加一行简短中文注释，使登录、进页、读取、扫描、计算、提交、校验、写回、保存、通知等步骤能够快速扫读。注释说明业务意图，不逐行复述代码；普通影刀 API 调用、简单赋值、显而易见的判断和日志语句无需单独加注释。市场指令仍按“功能 + 参数说明”的专项规则执行。
11. 已知参数名时严格使用现有名称；新增 `args` 参数使用最小、直观、稳定的名称；输入形态不确定时只在 `main(args)` 边界归一化一次。
12. 异常处理只覆盖明确需要处理的失败，不静默吞错。直接继续失败时使用 `raise`；补充业务上下文时使用 `raise ... from exc`；`traceback.format_exc()` 用于记录异常现场，`raise` / `raise ... from exc` 用于异常传播，上层会统一记录完整堆栈时中间层不重复记录；异常路径的收尾不得覆盖原业务异常。
13. 健壮性只处理真实可能且业务明确要求处理的失败。正常业务 API 已能明确抛错时，直接依赖该失败，不增加等价的前置校验、全量预检、重复读取或多套兜底逻辑。
14. 业务日志应能够还原主要执行过程：记录关键业务阶段、影响流程走向的判断及原因、重要业务对象的最终结果，以及必要的异常现场。停止、跳过、重试等会改变执行路径的行为应说明原因；商品、订单、任务等对象日志带上定位所需的最小稳定上下文；成功日志尽量描述实际发生的结果，不只写“成功”。不要给简单赋值、普通 API 调用或没有独立排查价值的连续动作逐条打日志。
15. `step`、页码、停止原因、重试次数、连续命中次数、待重试集合等决定程序行为的业务状态继续由业务代码显式维护。多处持续重复日志上下文和格式时，应考虑提取日志格式函数或专门日志对象，统一稳定上下文、字段顺序、日志级别和异常输出；日志对象可以按实际需要增强日志能力，但只负责“怎么记录”，不得承担停止判断、重试决策、翻页逻辑等“怎么执行”的业务控制。原则：**业务过程显式，日志格式隐藏；日志对象负责怎么记录，业务代码负责怎么执行。**

需要查看变量内联、函数边界、异常收尾和业务过程日志的完整判断与示例时，读取知识库 `docs/coding-style.md`；以上规则已足以约束普通小改。

## xbot 与知识库

1. 不根据通用 Python 经验、旧项目记忆或名称相似度猜 xbot API、市场指令、页面字段、XPath 或命令。
2. 用户已给出或当前代码已确认的稳定调用优先原样沿用。只有新增、修改或排查相关行为且证据不足时，才按知识库 `llms.txt` 读取事实页的相关章节。
3. 调用任何市场指令（`xbot_extensions`）时，无论是 Flow 的 `processN(...)`、直接 Python API，还是通过别名导入后调用，都必须在调用点紧邻添加注释，至少说明该入口的业务功能，以及本次传入各参数的名称和含义；不得只保留裸调用。功能和参数说明必须来自知识库事实页、当前安装版本源码或用户已确认用法，不得根据函数编号、函数名或参数值猜测。
4. 网页相关问题查 `browser.md`，Win32 查 `win32.md`，Excel / WPS 查 `excel.md`；不机械加载与当前改动无关的全文。
5. 网页业务默认使用 `xbot.web`；等待明确异步条件，不靠不断增加固定 `sleep`。
6. 影刀日志使用 `from xbot.app import logging`；动态内容使用完整 f-string，异常堆栈使用 `traceback.format_exc()`。
7. 读取 / 迁移旧版可视化项目，或排查“应用文件已损坏”、flow 文件缺失、`package.sigstore` 等项目级问题时，使用 `.agents/skills/xbot-project-diagnostics/SKILL.md`；普通 Python 业务 bug 不触发。
8. `selectorsV2.xml` 是由影刀编辑器维护的元素库文件，Agent 不得创建、编辑、格式化、覆盖或补丁修改该文件，否则影刀编辑器会提示应用文件损坏。需要调整元素库时应通过影刀编辑器操作；业务代码只读取并使用项目中已有的元素库名称。

## 验证与同步

1. 按风险做最小必要验证；默认不新增测试或运行无关全量检查。高风险写入先确认范围和回退方式。
2. `shadowbot_sync_tool.py` 与 `package.json` 位于项目根目录。新增 `.py` 文件后默认运行 `python shadowbot_sync_tool.py`；只修改已有 `.py` 文件时，仅在用户明确要求同步时运行。
3. 同步脚本自动扫描 Python 文件，不接收文件列表或 `prepare` 子命令；同步不是 Git 操作，成功也不等于影刀编辑器内运行验证。
4. 验证失败时先区分代码、环境、依赖和路径问题，不为通过无关检查扩大修改。
5. 用户说 'push' 时指的是 git commit 并 push 到 GitHub / Gitee 远程仓库。执行前确认有改动需要提交，并使用清晰的 commit 信息。

## 安全与汇报

1. 不隐藏副作用，不通过吞异常、静默失败或模糊返回值让主流程看起来成功。
2. 不提交账号、密码、Token、Cookie、Webhook、客户数据或未公开地址；示例和日志必须脱敏。
3. 长期业务规则和设计决策写入项目已有正式文档。
4. 完成后简短说明修改内容和实际验证；只有未执行项会影响结果判断或本应执行但受限时才特别说明。新增 `args` 参数时列出参数名、含义和建议类型。
