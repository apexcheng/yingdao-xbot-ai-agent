# 业务流程组合实践

本页说明多个已验证的技术能力如何协作完成一条真实业务流程，**重点是调用顺序、数据流、模块边界和失败取舍**；不重复维护 Web、WPS、日志和通知的 API 或专项细节。开发其它业务时借鉴组合方式，不照搬这里的业务字段、状态或保存政策。

## 表格更新

### 真实来源与适用场景

- 来源：影刀编码版「【表格更新】跨镜补货表」；[GitHub 固定版本 3a78997](https://github.com/apexcheng/cross-border-replenishment-rpa/tree/3a7899764960435767553f9cf00076adb5f19f74)（2026-10）。
- 该业务程序已在其它机器执行（用户确认）；本页以固定提交中的源码为准，不复制整个项目，也不据此声称该提交已单独做过实机验收。该提交的 17 项模拟测试已通过。
- 适用：从多个 Web / ERP 下载数据，更新同一个 Excel / WPS 工作簿的多个 Sheet，并在结束后记录结果、归档日志、发送钉钉通知。

### 一轮业务怎么串起来

```text
开始
  → 选择 Chrome Profile，关闭历史 Page（保留一个）
  → 清理旧 WPS 进程，打开一次目标工作簿
  → 读取工作簿中的上次成功时间、各国销量数据截止日期
  → 按业务顺序处理需要更新的任务：
       雅仓库存                 → 下载 → RAW 覆盖
       Shopee 官方仓库存        → 两地区导出 → 合并写入 RAW
       妙手 ERP 发货明细        → 下载 → RAW 覆盖；保留本轮源文件路径
       C-ERP 产品库             → 下载 → RAW 覆盖；保留本轮源文件路径
       Shopee SKU 映射          → 两地区导出 → 合并写入 RAW
       三国销量                 → 复用 / 补下源文件 → 商品规格同步
                                → 计算日期销量 → 逐国写入
  → 保存同一目标工作簿 → 根据保存结果关闭 WPS
  → 如符合项目条件，生成历史快照
  → 钉钉发送本轮业务结果
  → 汇总中文业务日志，导出运行日志
```

这里是 **6 个处理入口、8 个受跟踪 Sheet**（三国分别记录结果）。任务集固定，主流程直接顺序调用，不为了复用异常处理而改成配置列表 + 循环；地区和国家在同一处理规则下需要遍历时使用循环。

**跨模块传递的是实际需要的数据，不是万能上下文字典。** 主流程持有一个目标 `workbook`；成功下载的妙手 / C-ERP 文件路径仅在本轮交给后续国家销量模块。若本轮因为跳过或失败没有取得该路径，国家销量模块按自身需要重新下载；不引入跨轮文件缓存。来源工作簿由各业务模块打开，目标工作簿最终由主流程统一保存。

### Web、数据、WPS 的连接点

1. **Web 获取**：雅仓、妙手和 Shopee 由各自模块处理页面；C-ERP 通过现有市场指令获取来源。需要网页登录时在登录页完成登录，**新建 Page** 再进入业务 URL，避免依赖登录后的不确定跳转。业务步骤中失败的 Page 保留供排查；已成功的业务 Page 关闭。通用页面加载与异常处理见 [Web 实践](web.md)。
2. **异步导出绑定**：本案例 Shopee 按任务分类、导出时间、文件名前缀识别候选，并在多条候选时失败，而不是取第一条；**并未采用导出前任务列表快照**。开发新项目默认优先参考 [Web 实践中的本轮导出绑定规则](web.md#绑定本轮导出任务)，不把本项目的时间匹配方式当作唯一标准。
3. **WPS 更新**：源文件和目标工作簿均使用 WPS 打开；目标工作簿只打开一次，各更新模块通过共享 `workbook` 写入指定 RAW 区。两地区文件合并时，仅首份保留表头，后续份跳过相应表头；国家销量按已有截止日期重算需要的日期，不覆盖其它业务区域。细节见 [Excel / WPS 实践](excel-wps.md)。
4. **计算与结果**：三国销量共用同一来源与计算结果，先准备各国写入内容，再按国家顺序写入并更新状态；与一般 RAW 全量覆盖属于不同更新方式。具体规格归一、数据口径、目标列布局为本项目专用，不直接移植。

### 已确认的保存和失败边界

- **独立任务**：一个数据源失败，记录该 Sheet 失败后仍允许执行其它独立任务；今天已成功的任务可按本项目上次成功时间规则跳过。
- **依赖任务**：三国共用来源和预计算；共同准备失败影响三国。逐国写入时，前一国失败则当前国家记失败、后续国家记“未执行”，已经处理完成的国家仍保留结果。
- **保存策略（本项目明确允许）**：即使部分更新失败，**也允许在本轮结束时保存已写入的工作簿内容**，包括发生异常前的部分写入；不自动回滚，不把这个选择推广为所有项目的默认策略。RAW 清空后若读取 / 写入失败，也可能把清空或部分写入保存，属于此项目已接受的业务取舍。
- **处理完成 ≠ 已保存**：各 Sheet 的成功记录先表示“处理完成、等待保存”；主流程 `workbook.save()` 成功后，运行结果中的 `saved` 才置为真。保存失败保留 WPS 现场，通知中不得称为“已保存”。
- **通知独立**：保存、快照、WPS 关闭或钉钉发送失败分别反映真实结果；不能因钉钉失败把已保存的业务结果改为失败。跨轮状态和通知的职责边界见 [跨轮次处理状态与重试](cross-run-state-and-retries.md)。

### 日志、通知与复用原则

- 运行日志采用 `【业务对象】操作：结果｜必要信息`，正常路径记录关键节点；最终失败保留一次完整堆栈。详见 [中文业务上下文日志](logging.md)。
- 状态区仅记录业务结果、处理时间和必要说明；日志文件与历史快照用相同的执行开始时间命名，不另外维护用于关联的业务字段。
- 钉钉消息按 Sheet 展示更新、跳过、失败及未执行结果，并区分保存状态；不要把代码级流水日志复制到通知中。详见 [钉钉通知实践](dingtalk.md)。
- **借鉴组合，不复制业务**：可参考“多来源 → 各自下载处理 → 共用目标工作簿 → 统一保存 → 结果通知”的调用关系；不要复制 Shopee XPath、店铺 ID、验证码流程、国家销量字段位置、截止日期初始化值、重试次数、快照数量或具体的保存失败策略。
- **需要具体实现才打开源码**：优先从本页理解全局，再按上面的文件索引选读 1～2 个模块。新增或修改 API 时以 [正式 API 文档](../../../../../xbot-api-docs/docs/browser.md) 及相应知识页为准，不用历史项目反推 API 契约。
