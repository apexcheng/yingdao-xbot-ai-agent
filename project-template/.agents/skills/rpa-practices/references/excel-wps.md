# Excel / WPS 表格实践

以下经验主要来自“多个数据源或多个更新任务写入同一目标工作簿”的项目。单个 API、单个数据源或各自保存到独立文件的任务，不要机械套用。

## 业务失败与保存边界

不要把“某个数据源失败是否继续”和“工作簿什么时候保存”混为一谈。分别依据当前业务的数据依赖与保存要求判断；不能把尚未成功落盘的结果当作成功。

## WPS 工作簿用法

多 Sheet 业务工作簿使用 `xbot.excel.open(file_name=str(target), kind="wps", visible=True, update_links=False)` 打开。多个模块共用工作簿时，可打开一次，将 `workbook` 传给实际需要它的模块；保存与关闭按当前业务处理。

直接调用 `workbook.save()`、`workbook.close()`，不要只为这两个调用单独增加 `try/except` 来包装、转换或吞掉异常；让异常遵循项目已有的业务流程。需要保证资源收尾时仍可使用 `finally`，但不对正常保存、关闭动作额外套专用捕获。

WPS 自动保存、保存失败或异常退出时，以正式文件的实际状态判断结果。

### 日期表头不要只依赖 `get_last_column()` 确定读取终点

真实案例（跨镜补货表）：三个国家 Sheet 的日期从 H1 开始，实际延伸到 NH1（2026-12-31），但影刀 WPS 的 `sheet.get_last_column()` 在该次运行中只返回 JJ；直接用 `get_range()` 读取 KA1:KC1（2026-10-07 至 10-09）则正常。程序据此误报「缺少日期列」。

**处理方式**：对于这种起始日期已知、表头按天连续排列的业务，根据本轮所需的最晚日期与首列日期的天数差确定读取终点，再按列分段读取和建立日期映射；不要仅以 `get_last_column()` 的返回值截断日期表头。

这仅证明该工作簿、该次运行的最后列判断不完整，**不证明 `get_last_column()` 普遍只支持到 JJ 列**，也不能据此断定原因是固定列数限制。

## 数据源模块

独立数据源具有清楚的业务边界或实际复用价值，且拆出后更容易阅读时，可以建立模块，不以代码行数为门槛。同类模块可统一采用 `update_xxxx.py` 命名；入口只接收实际需要的页面、会话、配置或目标工作簿，不传入包含所有状态的大字典。若一类业务更新需要复用多个国家 / 站点的同一计算规则，可由一个业务模块集中实现。

成功协议只选一种：

- 成功正常返回，失败抛出异常；或
- 项目已有显式布尔协议时，主流程严格检查 `is True`。

不混用“部分函数抛异常、部分函数返回 `None`、部分函数返回布尔值”的成功判断。

## Excel 写入安全

- 覆盖目标区域前，依据本轮已有数据确定实际要写入的表头、列映射及区域；空结果是否覆盖由业务决定，不重复读取或做无关全量预检。
- 覆盖型数据：只清空约定的数据区域，不整表 `clear()`，避免删除公式、格式和其他业务区域。
- 追加型数据：先确认最后日期或最后数据行，只追加缺失数据。
- 商品 ID、订单号、链接 ID 等长数字写入前按文本处理，避免精度丢失。
- 下载步骤必须检查返回路径非空且文件存在。网页后台异步导出时按 [本轮导出任务绑定](web.md#绑定本轮导出任务) 定位对应文件。
- 更新状态表只读取本次业务判断需要的字段，不自动补齐无关字段。
- 一个工作簿会话内先更新原始区、后读取公式计算区的项目，应在真实 Office / WPS 中验证公式是否刷新；不得以 Python 模拟成功替代真实公式结果验收。

Excel / WPS 具体 API 见 [excel.md](../../../../../xbot-api-docs/docs/excel.md)。
