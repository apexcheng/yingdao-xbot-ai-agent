# 网页自动化实践

## 页面状态与业务数据获取分离

**业务事实数据取数优先级：网页网络响应 → DOM 数据提取。** 能从 XHR / Fetch 等响应中读取完整、可信的业务数据时，不再滚动虚拟列表或逐行读取网页元素。**登录状态、当前登录店铺名称、按钮可用状态等属于页面状态核验**，可直接用已确认的 XPath / DOM 读取，不需要先探测网络响应或询问是否放弃网络取数。由网页自身触发请求，不等于必须由 RPA 单独构造 HTTP 请求。

多店铺独立浏览器环境的身份校验顺序：**切换 Profile → 检查登录 → 读取实际店铺名称 → 匹配配置 → 开始采集**；不能仅凭 Profile 判断当前登录店铺。

**区分页面返回数据的三层来源**：列表等查询通常在 XHR / Fetch 响应中；基于 SSR（服务端预渲染）的详情页可能把结构化业务数据直接嵌入首次 HTML（如 `__NEXT_DATA__`），不能把它误认为已经单独验证过同名后端 API；发货轨迹、客服聊天等也可能由页面加载后另发 XHR 获取。按真实页面和响应分别确认来源、字段结构、页内身份关联和完整性，再决定最少的读取路径；并非所有数据必须由 RPA 再构造一遍请求。订单号、售后单 ID、物流运单号属于不同身份，**原发货签收**与**退货签收**属于不同物流方向，尤其不可因为字段都含 `SIGN` 就混用。聊天记录如返回序列化 JSON 字符串，应先按实际数据类型解析；样本中 `messageList` 条数等于 `total`，不能证明其他订单不分页。不要将单笔成功探测冒充跨店、跨售后类型的正式运行验收。

1. 先确认目标业务数据是否随网页请求返回，核实响应结构、必要字段与时间单位；请求包通常携带查询条件，实际业务数据应优先从**响应包**读取。
2. **先启动网络监听，再执行 DOM 动作**，等待该动作对应的响应后解析数据；查询、翻页均依此重复。影刀原生 `start_monitor_network()` / `get_responses()` / `stop_monitor_network()` 用法见 [browser.md](../../../../../xbot-api-docs/docs/browser.md#23-网络监听和请求)。
   JSONP 常通过 `Script` 返回，按实际资源类型监听并解析回调体；按 API 与 `pageNo` 关联分页响应。首屏可能预加载其他页签，导航前先监听，切换页签没有新请求时检查已有响应。
3. 同一份业务数据不要再从 DOM 读取并交叉等待，避免虚拟滚动、元素刷新和重复解析；但 DOM 仍可用于确认按钮状态、触发下一页。
4. 只有请求响应加密、缺少必要字段、无法可靠取得等情况被核实后，才降级 DOM 提取，不默认同时维护两套提取方案。接口契约未核实时，不猜测字段名或将错误数据写入业务文件。
5. **用户给出用于读取业务事实数据的 XPath 时**，不要为此打开浏览器或探测网络响应，直接问用户：**「确认不通过网络响应，而是使用 XPath 提取数据吗？」** 用户确认后按 XPath 方案执行，未确认前暂停该业务取数方案；用于交互（查询、翻页、排序等）以及登录状态、店铺身份等页面状态核验的 XPath 直接使用，无需询问。定位依据仍须遵守 [网页探测 Skill](../../web-workflow-extraction/SKILL.md)，不能凭猜测构造。

### 网络监听的触发边界

网络监听的目的，是捕获某个页面动作实际触发的目标请求。应采用「先监听 → 触发请求 → 读取目标响应 → 立即停止监听」的最短链路，不为了获取接口数据而默认刷新页面。

- 能通过点击、确认、切换筛选、切换指标等页面动作触发目标请求时，应在该动作之前开始监听，拿到目标响应后立即停止。
- 只有目标接口主要随页面初始化发送，且没有已确认的其他页面动作可以重新触发时，才使用 `reload()` 触发请求。
- 监听 URL 应尽量限定到实际目标接口，不长期监听大范围路径，避免积累无关响应并增加后续 `get_responses()` 的遍历成本。
- 同一页面需要采集多个接口时，不应机械地为每个接口执行一次刷新；应根据各接口真实触发条件分别监听。
- 页面当前已处于目标状态时，再次点击同一选项可能不会产生新请求。例如当前已选「近8小时」，需要重新获取该模式响应时，可先切换到另一时间范围，再切回目标范围，以明确触发请求。
- 对连续切换指标的场景，可按每个指标执行「开始监听 → 切换指标 → 获取响应 → 停止监听」，避免整个采集过程持续保留网络监听。

典型流程：

```text
页面初始化接口：开始监听 → reload → 获取响应 → 停止监听
配置确认接口：完成配置 → 开始监听 → 点击确认 → 获取响应 → 停止监听
筛选 / 指标接口：开始监听 → 切换筛选或指标 → 获取响应 → 停止监听
```

原则：**刷新只是触发请求的一种方式，不是网络监听的固定步骤。优先使用最直接的真实页面动作触发目标请求。**

以下是后台异步导出任务及动态页面的专项经验。

## 绑定本轮导出任务

同一时间窗口可能已有历史导出任务，默认通过**导出前任务列表快照 + 导出后新增任务比对**识别本轮目标：

复用历史报表须检查起止时间完整覆盖目标区间，不能只比较日期；导出弹窗继承页面筛选时先设定时间范围。明确强制新建时可跳过首次历史查询，但提交后仍须唯一定位本轮任务。

1. 导出前读取当前任务列表作为快照，再执行导出动作；若平台直接返回可靠、可追踪的唯一任务 ID，可以使用该 ID，不必额外读取快照。
2. 导出后查询任务列表，与快照比对新增任务；可结合任务 ID、唯一任务名、文件名和任务分类识别本轮目标。无法直接确定时，再使用本轮触发时间辅助筛选。
3. **候选必须唯一**，才能等待它变为可下载状态并点击对应下载；多条同时匹配或无法区分历史任务时直接报错，不选第一条。
4. 取得本轮下载的文件路径后直接交给业务处理；不额外验证文件存在性、表头、第一行或业务结构。

压缩包解压与多文件目标识别参阅 [xzip.md](../../../../../xbot-api-docs/docs/xzip.md)；网页下载和等待 API 参阅 [browser.md](../../../../../xbot-api-docs/docs/browser.md)。

## Page 与下载操作

- 需要优先使用后打开的目标 Page，且已确认新页面排在 `web.get_all()` 返回列表后部时，倒序遍历并取第一个符合 URL / 标题条件的页面。
- 未登录时先完成登录，登录成功后**新建 Page 打开目标业务 URL，并关闭旧登录 Page**；不依赖登录 Page 自动跳回原网址。
- 非表格更新场景，需要重试的下载操作最多执行 3 次（首次加 2 次重试）；下载失败时重试完整下载过程，不为重试额外增加框架。表格更新按 [表格操作 Skill](../../spreadsheet-operations/SKILL.md) 执行整个 Sheet 最多 2 次尝试，不套用这里的下载重试次数。
- Page 新建、跳转、刷新后，先 `page.wait_load_completed()`，再 `time.sleep(2)`，再操作业务页面；启动清理 Page 的规定见项目 `AGENTS.md`。

**GUI 并发限制（2026-11-04 实测）：**不要依赖 Python 多线程或多进程实现影刀 GUI 操作的真正并行。同一影刀任务中，Profile 1 的 Bing 模拟输入持续 30.44 秒，Profile 2 的百度点击调用等待 30.79 秒、直到输入结束才完成，表明 `xbot.web` 多线程操作会互相阻塞；即使使用不同 Chrome Profile，也不能把线程调用时间重叠视为实际并发。**多进程尚未实测**，不应写成已证实不支持，但同样不能未经验证就作为并发优化方案；默认按 GUI 操作串行设计。

## 批量配置与元素操作性能

配置页需要连续勾选、取消或切换一批同类元素时，先拆分真实耗时，不要只盯 XPath。影刀元素操作的 `delay_after` 会在循环中逐次累计；例如复选框 `check()` 未显式缩短等待时，二十次切换就可能产生约二十秒固定等待。页面已实测允许更短间隔时，应显式设置合适的 `delay_after`（例如 `0.3` 秒），先优化真正占时的操作等待，再考虑缩短 XPath timeout；`timeout` 是最长查找时间，元素立即存在时并不会固定等待到超时。

同一配置面板有一组同类元素时，优先一次 `find_all_by_xpath()` 获取完整元素列表，并在本轮操作中缓存 `Element + 业务值/value + 当前选中状态`。后续直接复用已取得的 Element，不为每个指标再次 `find_by_xpath()`，也不反复调用 `get_attribute()`、`is_checked()` 读取没有变化的状态。若页面操作会重绘 DOM、导致元素失效，再按「动态任务表」规则重新定位；不要为尚未发生的失效预先放弃批量复用。

指标、字段等配置项存在稳定页面顺序时，让页面 DOM 顺序决定处理顺序：一次读取全部配置项，过滤程序已知且需要处理的项目，跳过平台后来新增但程序未知的项目，再按页面顺序分批处理。第一批、后续批次尽量走同一套逻辑，不为默认选中状态单独维护一条分支；若页面存在每批最少/最多数量限制，只在最后不足最低数量时，用已处理项目补足页面要求，真正业务结果仍只计本批新处理项目。

验证只保留最接近最终业务结果的一层。若「切换页面配置 → 确认 → 后端响应返回实际选中项」已经能严格证明最终状态，就不要在确认前再完整遍历一次 DOM 做相同的二次验证；已有响应等待函数时，也不要为同一完成条件额外叠加固定等待。删除的是重复验证，不是最终结果校验：最终响应仍须与本批目标匹配，失败应如实抛出。

## 动态任务表：避免过期网页元素

React / SPA 后台任务中心可能在数据刷新时替换整行 DOM。实测 Shopee 中，保存 `row` 或 `td` 的影刀元素对象后，再调用 `get_text()` 或 `click()` 可返回 Code 106（元素 ID 失效）。不要把它简单归因为 XPath 错误、广告遮挡或等待时间不够。

- 每次轮询重新查询当前任务列表；动态变化快时，可通过 `page.execute_javascript()` 在**当前 DOM** 中一次读取行文本，拿到普通数据后再判断。
- 已确认采用 DOM 提取时，在同一次当前 DOM 读取中取得目标表格的表头和行数据，按已核实的表头名称确定所需列的位置，不把固定 `td` 下标当作字段含义。每个必需表头须恰好匹配一处；缺失或重名时明确报告解析错误，不取首个匹配、不回退固定下标，也不将解析失败返回为空任务列表。字段名及别名以当前项目确认结果为准。表头唯一性检查可参考[库存监控源码快照](../../../../../reference-projects/inventory-monitor/snapshot/pdd.py)，具体页面选择器不直接照搬。
- 按表头位置读取单元格前，确认表头与数据行的列位置一一对应。JavaScript 数组从 0 开始，CSS `:nth-child(n)` 从 1 开始且计数所有元素兄弟；只有数组与选择器对应同一父节点下相同顺序的元素集合时，才能按 `n - 1` 换算，不能直接套用于经过筛选的 `td` 集合。
- 准备点击下载时重新定位本次唯一任务，不能长期持有上轮的 WebElement。
- DOM 读取只能解决陈旧元素引用问题，不能替代“本轮唯一任务”的业务判断；XPath、选择器及点击方式应按当前真实页面验证。
- 遇到 Code 106 时先确认页面有无重绘、弹窗遮挡、登录跳转或 Profile 切换，再决定最小修复，不把 JavaScript 点击写成万能 fallback。
