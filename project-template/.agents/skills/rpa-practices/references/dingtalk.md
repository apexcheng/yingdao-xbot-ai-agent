# 钉钉通知实践

本页约束业务自动化项目中的钉钉通知**怎么写得清楚、可用于执行汇总和运维追溯、方便快速处理**。新项目简单群通知优先使用[钉钉 Webhook 功能模板](feature-templates/dingtalk-webhook.md)；现有项目若仍调用「增强工具2026」，其旧接口签名与返回值见 [增强工具 API 事实](../../../../../xbot-api-docs/docs/extensions/xbot-enhance-tools.md)。Webhook 不能替代企业机器人私聊/图片能力。

## 1. 总体风格

- 默认使用 Markdown，优先让接收人第一眼看到“发生了什么、结果怎样、是否需要处理”。
- 通知是业务结果，不写成程序日志。少写技术过程、内部状态码、变量名和无关堆栈。
- 文案简洁但信息完整。需要定位问题时，保留平台、店铺、商品 / SKU、操作时间、失败原因等最小必要上下文。
- emoji 用来做视觉分区和状态识别，不做装饰。相同含义尽量固定使用相同 emoji。
- 重要数字、结论、状态使用 `**加粗**`；普通说明不要整段加粗。
- 多条结果按“状态”分组，再按业务对象逐条展示，不把所有字段堆成一大段。
- 对涉及计算、分配、判断的关键业务结果，按需说明主要依据、限制条件和计算结论，便于运营判断“为什么是这个结果”；简单通知不额外堆计算过程。

常用状态语义参考，不要求每条通知使用完整的 emoji 集合：

- `✅`：成功、完成
- `⚠️`：需要关注，但不一定是程序故障
- `❌`：失败、终态失败
- `🔁`：后续会重试 / 待重试
- `🚨`：程序异常或需要运维立即关注

时间、店铺、商品及正向汇总等 emoji 依场景使用，参考下方 Demo。

## 2. 推荐结构

内容较多的业务通知可按以下顺序组织；短消息只保留实际需要的部分：

1. **标题：业务对象 + 当前结论**
2. **顶部汇总：最重要的数量 / 状态**
3. **分类明细：成功、失败、需关注项分别展示**
4. **依据、原因 / 后续动作：只在有业务价值时出现**
5. **分隔线 + 通知时间**

标题不要只写“通知”“执行结果”“任务完成”。优先写成：

```text
拼多多 / BOW旗舰店｜库存处理完成✅
天猫 / BOW旗舰店｜库存处理中断⚠️
库存监控阶段汇总⚠️
天猫 / BOW旗舰店｜程序异常🚨
```

## 3. 具体偏好

### 3.1 先给结论，再给过程

顶部先回答接收人最关心的问题，例如成功多少、失败多少、哪些需要人工关注。不要先写“程序于 xx 时间开始运行”“本次共扫描 xx 条消息”等过程信息。

推荐：

```text
> 🎉 补库存成功：**8 个 SKU**　❌ 最终失败：**1**
> ⚠️ ERP库存不足：**2**　ℹ️ SKU未上架：**1**
```

### 3.2 明细按状态分组

当一条通知包含多种结果时，用四级标题分组，让运营先看异常，再按需查看成功项。

```text
#### ✅ 补库存完成
#### ❌ 处理失败
#### ⚠️ ERP库存不足
#### ℹ️ SKU未上架
```

不要对每个 SKU 重复一整套“成功 / 失败 / 建议”标题。

### 3.3 同类业务对象字段顺序一致

同类通知中的字段顺序尽量一致，便于扫读。下面仅为库存 / 商品类示例，不规定其他业务的字段：

```text
商品 → 规格 → 商品ID → 规格ID → 消息时间（如有）→ 操作时间 → ERP映射 → 关键结果
```

示例：

```text
**1. 📦 三模蓝牙键盘**
🏷️ 规格：黑色 / 双模
🔢 商品ID：123456
🆔 规格ID：987654
🕒 消息时间：2026-09-16 18:25:00
🕒 操作时间：2026-09-16 18:30:21

🧩 ERP商品：K500D
🏷️ ERP规格：6927000000000｜黑色双模

📊 库存：**2 → 10**　➕ **+8**　🏭 ERP：86
```

能生成商品详情链接时，优先把**商品名称本身**做成链接，不额外增加一行裸 URL。
若业务同时涉及“收到预警 / 下单时间”和“实际执行时间”，分别标明，避免把历史消息误读为刚刚发生；不需要的时间字段不出现。

### 3.4 失败原因与执行现场

失败、风险和人工关注原因使用引用块突出，不埋在普通字段中。

```text
> ❌ **失败原因**：库存编辑页提交后未检测到库存变化
🔁 下轮继续重试（2/3）
```

如果已经是终态：

```text
> ❌ **失败原因**：未找到对应 ERP 规格映射
🔁 已终止自动重试
```

失败项说明业务对象、失败阶段、关键原因、未完成范围以及后续是否继续；必要时可附短错误码或元素名，避免只有孤立的 XPath 错误。完整 traceback 留在日志；只有面向开发 / 运维且确有必要时，才额外提供技术现场。

### 3.5 @ 只用于需要人处理的通知

不要把每次成功、普通跳过或仍会自动重试的临时失败都 @ 人。

优先在这些情况 @ 对应负责人：

- 已进入终态失败，需要人工处理。
- 库存、映射、账号等业务条件不足，需要运营介入。
- 程序异常，需要运维排查。
- 待重试项长期找不到，自动流程无法自行恢复。

按处理职责选择 @ 对象：业务条件需处理时 @ 对应运营，程序或数据链路异常时 @ 运维；需要双方协作时可同时 @，并避免重复手机号。**是否发送异常通知与是否 @ 人是两个决定。** 临时、可自动恢复的异常是否直接通知遵守项目规则；明确要求“所有运行异常均可通知”的任务，首次失败也须进入钉钉（可以合并到本轮对象报告），重复异常可按已确认规则降噪，不能直接略过首次。不要把某个项目的连续失败次数、提醒间隔写成通用阈值。

### 3.6 通知时间与收尾

较长通知可在正文结束后使用分隔线、统一展示时间；简短通知无需强制分隔线：

```text
---
🕒 **通知时间**：2026-09-16 18:31:05
```

阶段汇总需要明确统计区间时，可以展示“统计区间 + 汇总时间”。

### 3.7 关键业务结果解释“为什么”

库存、价格、配额等经过业务计算的结果，优先展示**操作前后值 → 决策依据 → 限制条件 → 最终目标**；需要核对算法时再补简短计算链。例如：ERP 可售、安全底仓、可释放库存、销量占比如何共同决定目标库存。不要把原始记录、程序变量、完整算法日志全部粘进消息。

未执行操作的对象也要写清业务原因，例如“ERP 库存不足”“SKU 未上架”“命中忽略名单”，而不是统一写成“跳过”。如果有可直接处理的入口，可在商品名或“维护名单”上嵌入链接。

### 3.8 区分业务结果、程序异常与阶段汇总

- **适用范围**：已配置执行结果通知或明确要求执行报告的任务，通知首要用途是**汇总执行事实、支持运维追溯**；不强制所有自动化都新增通知。
- **逐对象和逐阶段**：多店铺、多商品或多 Sheet 的执行报告，先给总数，再按有意义的业务阶段列出每个应执行对象的结果；不能只报“总共 0 条”，使人无法判断哪家失败。简单单对象通知仍可简短。
- **状态准确**：区分成功、正常跳过、部分完成、异常失败、权限不足、限流停止、尚未执行等语义；这不是要求所有项目新增统一数据库枚举。前序中断导致下游未运行时，应写“未执行（前序中断）”，不能凭猜测写“未到执行时间”或“正常跳过”。
- **数量与事实边界**：明确区分实际取得数、实际新增/更新数、成功场次和失败场次。成功采集但无需更新时可以为 0；未执行时的 0 不是失败也不是采集成功。部分完成后中断仍要保留已确认成功的对象和写入成果，不得整批改报“全部失败”。
- **失败与后续**：按对象写明失败阶段、简短原因、已跳过/待重试/已停止的实际处理结果；不可从异常自行推断重试计划。程序异常或权限不足需指出受影响对象与范围，完整堆栈留日志。
- **本轮与历史**：本轮新成功、依据历史成功跳过的对象分别表达；后者注明「上次成功」时间，不计作本轮新完成。普通跳过是否独立发送通知由业务决定，但**已发送的执行汇总不能隐去影响结果判断的跳过和未执行对象**。
- **运行信息**：可追溯执行报告附实际开始与结束时间；需要跨系统定位时复用已有任务 ID 或日志引用，不为通知新建持久化状态、日志系统或通用 Report/Manager 层。
- **异常出口覆盖**：已要求异常告警的项目应沿初始化、接口/数据读取、页面操作、单对象处理、解析、重试、降级和收尾路径检查通知入口；`except` 后继续、返回正常结果或使用旧数据都不代表异常可以从通知中消失。正常无消息、业务允许跳过等不自动归为程序异常。
- **异常与业务结果并存**：单个对象本轮失败但仍可重试，应写“本轮失败 / 待重试”，不能误报为最终失败；解析失败无法关联对象时也应保留错误原因。程序继续运行或阶段汇总时，已发生的异常、降级和受影响对象仍应可见，不能因业务写入数量为 0 就省略异常报告。
- **通知失败与补发**：发送函数失败时不能报告已送达；保留明确的失败日志。需要跨轮可靠补发的项目，保存必要的通知正文与发送状态，后续成功再清除待发送项；若连状态保存也失败，应留下独立的明确错误。机器人接口调用成功只证明请求侧成功，不代表接收人已阅读。不得以通知失败为理由重做已成功的业务操作，也不为此默认新增复杂队列框架。

可重试业务错误与终态失败的区分、跨轮次计数以及通知失败后的进度持久化，见[跨轮次处理状态与重试](cross-run-state-and-retries.md)。通知发送失败不能倒改已成功的业务结果；是否重新发送通知，应由该业务已有的发送进度规则决定。

## 4. Demo

### Demo 1：店铺处理结果

示例数字用于演示信息层级和可解释的计算链，不代表真实库存阈值或所有项目必须采用的分配算法。以下失败项为终态失败，不与“下轮仍会自动重试”混写。

```markdown
### 拼多多 / BOW旗舰店｜库存处理完成⚠️

> 🎉 补库存成功：**3 个 SKU**　❌ 处理失败：**1**
> ⚠️ ERP库存不足：**1**

#### ✅ 补库存完成

**1. 📦 三模蓝牙键盘**
🏷️ 规格：黑色 / 双模
🔢 商品ID：123456
🆔 规格ID：987654
🕒 消息时间：2026-09-16 18:25:00
🕒 操作时间：2026-09-16 18:30:21

🧩 ERP商品：K500D
🏷️ ERP规格：6927000000000｜黑色双模

📊 平台库存：**2 → 10**　➕ **+8**
🏭 ERP可售：**86**｜安全底仓：**20**｜可释放：**66**
🎯 目标库存：**10**
📈 销量依据：SKU 3天/7天 = **6 / 14**｜69码 3天/7天 = **12 / 28**
📊 销量占比：3天 **50%**｜7天 **50%**｜加权 **50%**
🧮 计算：需求池=ceil(28÷7×5)=**20**；库存池=min(20,66)=**20**；ceil(20×50%)=**10**
⚙️ 分配模式：**销量动态**

#### ❌ 处理失败

**1. 📦 无线键鼠套装**
🏷️ 规格：曜石黑
🔢 商品ID：223344
🆔 规格ID：556677
🕒 消息时间：2026-09-16 18:27:00
🕒 操作时间：2026-09-16 18:30:48

> ❌ **失败原因**：提交后未检测到库存变化
🔁 已终止自动重试

#### ⚠️ ERP库存不足

**1. 📦 折叠键盘**
🏷️ 规格：深空灰
📊 平台库存：**1**　🏭 ERP可售：**4**　未补库存
> ⚠️ **未操作原因**：ERP 可售低于本次业务要求

---
🕒 **通知时间**：2026-09-16 18:31:05
```

### Demo 4：多店铺自动化执行汇总（含未执行与历史权限不足）

以下数据仅为格式示例；不同任务按真实业务阶段、对象和数据粒度选用字段，不强制采用“实时/历史”分段。

```markdown
### 直播分钟采集｜部分完成⚠️

> 实时写入/更新：**120 条**　历史写入/更新：**2350 条**

#### 实时采集
- **店铺A**｜成功：获取 **481 分钟**，写入/更新 **120 条**
- **店铺B**｜正常跳过：当前不在正在直播列表，**本轮未采集**

#### 历史补采
- **店铺A**｜成功：补采 **3 场**，写入/更新 **2350 条**，失败 **0 场**
- **店铺B**｜权限不足：**1 场未补齐**，已停止该店铺本轮剩余历史日期检查
  > ⚠️ **原因**：当前登录账号无法进入该直播间复盘模式

#### 执行说明
> 历史阶段部分未完成；已写入的数据保留，未核实的分钟不作为已采集或未开播数据上报。

---
🕒 **执行时间**：2026-10-28 01:00:00 ～ 01:12:30
```

如果店铺A在实时采集第一步异常退出，则店铺B应标记「未执行（尚未轮到）」，历史阶段标记「未进入（实时阶段中断）」，**不可把二者写成正常跳过或未到巡检时间**；异常说明应指明店铺A、实时指标定位步骤及简短错误原因。
